# Topic 3.3: Decentralized RPC and Failover Networks

The source of truth for lesson 3.3. The lesson script (`3.3.md`) and the code may only teach what this
file says. Facts carry a source tag; anything else is marked (unverified).

## In one sentence

Decentralized applications and wallets achieve speed and resilience by racing queries across independent RPC providers and automatically failing over when individual nodes slow down, rate-limit, or drop offline.

## The problem it solves

If a dApp or wallet relies on a single Remote Procedure Call (RPC) endpoint, any outage, rate limit, or network censorship at that provider breaks the entire application. During network congestion, relying on one node leads to false "transaction failed" warnings and sluggish user experiences. [near-rpc]

## How it works on NEAR

**NEAR JSON-RPC Protocol.**
- Applications interact with the blockchain through standard HTTP/JSON-RPC requests (`broadcast_tx_commit`, `query`, `block`, `EXPERIMENTAL_tx_status`). [near-rpc]
- All endpoints support open Cross-Origin Resource Sharing (`access-control-allow-origin: *`), allowing client-side browser apps to connect directly without backend servers. [spike-3]

**Independent RPC Providers.**
- **FastNEAR:** High-throughput, performance-optimized public RPCs (`rpc.testnet.fastnear.com`, `test.rpc.fastnear.com`, `rpc.mainnet.fastnear.com`). No aggressive rate-limit headers in testing. [spike-3]
- **NEAR Foundation:** Reference infrastructure (`rpc.testnet.near.org`, `rpc.mainnet.near.org`). [spike-3]
- **Community Providers & Aggregators:** DRPC (`near.drpc.org`), 1RPC, POKT. [spike-3]

**Archival vs. Regular Nodes.**
- Regular RPC nodes store the state history for only the last **5 epochs** (roughly 2.5 days) to keep disk requirements manageable. [near-rpc]
- Historical queries (such as looking up transactions or blocks from weeks ago) must be directed to specialized **archival nodes** (`archival-rpc.testnet.fastnear.com`). [spike-3]

**Client-Side Racing & Failover.**
- Libraries like `near-kit` support a list of `fallbackRpcUrls`. [spike-3]
- If the primary provider returns a 429 (rate limited), 503 (service unavailable), or times out, the client immediately retries the request against the next provider in the pool. [spike-3]
- Advanced clients use "hedged requests" (or racing): dispatching read queries to two providers simultaneously and using whichever returns a valid response first. [near-rpc]

## Words to know

- **RPC (Remote Procedure Call):** The network gateway allowing applications to query blockchain state and submit transactions.
- **Failover:** The automatic switching to a redundant or backup provider upon the failure of the primary provider.
- **Archival Node:** A full node that preserves the complete historical record of the chain from the genesis block.
- **Epoch:** A continuous period of blocks (~12 hours on mainnet, ~43,200 blocks) during which validator seats remain fixed.
- **Rate Limit:** Restrictions enforced by server operators limiting how many requests an IP address can make per minute.

## Common misunderstandings

- **"The RPC is the blockchain."** No. An RPC node is merely a window looking into the network. If an RPC node goes down, the blockchain itself continues producing blocks uninterrupted. [near-rpc]
- **"All RPC nodes hold the entire history of the chain."** No. Standard RPC nodes discard data older than 5 epochs. Only archival nodes retain full historical state. [near-rpc]
- **"Every provider responds with the same latency."** Latency varies significantly based on server location, caching layers, and load. [spike-3]

## Compared with Ethereum

- **Ethereum:** DApps traditionally depend heavily on centralized infrastructure monopolies like Infura and Alchemy. If Infura suffers a localized outage, large portions of Ethereum dApps go dark simultaneously. [eth-infura]
- **NEAR:** Ecosystem benefits from multiple free, high-performance public providers like FastNEAR alongside foundation and aggregator nodes with open CORS by default. [spike-3]

## Strengths and weaknesses (feeds the Honest take)

**Strengths:**
- Built-in browser accessibility: Open CORS across major providers lets browser dApps query multiple nodes with zero API keys. [spike-3]
- Strong public infrastructure: FastNEAR provides fast, unthrottled public endpoints. [spike-3]

**Weaknesses:**
- Ephemeral providers: Several historical providers (such as Lava or Ankr public endpoints) have deprecated or closed endpoints over time, requiring active list maintenance. [spike-3]
- State discrepancy: Fast-moving shards can occasionally result in slight block height drift between providers during active re-orgs or network latency. [near-rpc]

## What the lesson must show

1. Display 3 active testnet RPC endpoints side by side (FastNEAR, NEAR Foundation, Fallback).
2. Race the nodes: send a simultaneous state query (`status` or `block`) and measure latency round-trip in milliseconds.
3. Simulate provider failure: intentionally drop or intercept the fastest provider.
4. Watch the application's client failover seamlessly to the secondary node without user disruption.
5. Contrast query results between a standard RPC node and an archival node for a historical block.
