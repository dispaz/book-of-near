# Topic 3.2: Fungible Tokens (NEP-141), Storage Registration (NEP-145) and Meta-Transactions (NEP-366)

## In one sentence

NEAR fungible tokens (NEP-141) protect contract creators from storage exhaustion by requiring a tiny one-time storage registration deposit (NEP-145), and support gasless user interactions through native protocol meta-transactions (NEP-366).

## The problem it solves

1. **Storage Exploitation (State Bloat Attack):** On Ethereum, anyone can airdrop dust ERC-20 tokens to millions of addresses for free, leaving node operators to shoulder the burden. On NEAR, because contracts pay storage staking (Topic 3.1) for every entry in their balances table, an attacker sending dust to 100,000 users would bankrupt the token contract's NEAR reserves. [near-storage-mgmt]
2. **The Gas Onboarding Wall:** Users receiving a token often cannot move or use it because they have zero native currency (NEAR) to pay transaction fees. [near-meta-tx]

## How it works on NEAR

**NEP-141: The Fungible Token Standard.**
- NEAR's equivalent of ERC-20. [near-nep141]
- Core methods include `ft_transfer`, `ft_transfer_call` (transfer and call a contract in one workflow), `ft_total_supply`, and `ft_balance_of`. [near-nep141]

**NEP-145: Storage Management & Registration.**
- To prevent storage exhaustion, a token contract does not allocate state for an account until a **storage deposit** is paid. [near-storage-mgmt]
- A user (or someone on their behalf) calls `storage_deposit` with a tiny attached deposit (typically ~0.00125 NEAR, covering the bytes required to store account balance and keys in the contract's trie). [near-storage-mgmt]
- If an account is not registered, calls to `ft_transfer` sent to that account will fail by default, preventing un-sponsored state allocation. [near-storage-mgmt]
- When an account empties its balance and unregisters (`storage_unregister`), its locked storage deposit is fully refunded. [near-storage-mgmt]

**NEP-366: Native Meta-Transactions.**
- Built directly into the NEAR protocol runtime (no custom wrapper contracts or external smart contract wallets required). [near-meta-tx]
- A user signs an off-chain payload called a **`SignedDelegateAction`** authorizing an execution (such as `ft_transfer`). [near-meta-tx]
- A third party, known as a **Relayer**, packages this payload into a standard transaction, attaches the required NEAR for gas fees, and broadcasts it to the network. [near-meta-tx]
- The protocol verifies the user's signature, executes the action as the user, and charges the gas fee to the relayer. The end user pays zero native NEAR. [near-meta-tx]

## Words to know

- **NEP-141:** The standard specification for fungible tokens on NEAR.
- **NEP-145:** The storage management standard defining `storage_deposit`, `storage_withdraw`, and `storage_balance_of`.
- **Storage Deposit:** The fractional NEAR deposit required to register an account record in a contract's storage.
- **Meta-Transaction (NEP-366):** An action signed by an account and submitted by a relayer who pays the gas.
- **Relayer:** A service or server that submits user-signed meta-transactions to the chain and covers gas costs.

## Common misunderstandings

- **"You must pay a storage deposit on every token transfer."** No. You only pay once when an account is first registered with that specific token contract. Subsequent transfers incur only normal gas fees. [near-storage-mgmt]
- **"Meta-transactions require deploying a smart contract wallet."** No. On Ethereum, meta-transactions historically required ERC-4337 or Gnosis Safe contract wallets. On NEAR, standard named and implicit accounts natively support delegate actions in the protocol. [near-meta-tx]
- **"The relayer can alter the user's transaction."** No. The relayer only transmits the cryptographic signature of the `DelegateAction`. Any tampering invalidates the signature and causes the transaction to fail. [near-meta-tx]

## Compared with Ethereum

- **Ethereum (ERC-20 + ERC-4337):** ERC-20 balances can be written for any recipient without upfront storage deposits. Gasless transfers require complex account abstraction infrastructure (Bundlers, Paymasters, EntryPoint contracts). [eth-aa]
- **NEAR:** NEP-145 protects token creators from storage drain by requiring a tiny upfront storage registration. NEP-366 provides protocol-native meta-transactions natively supported by all accounts. [near-meta-tx]

## Strengths and weaknesses (feeds the Honest take)

**Strengths:**
- Native gasless onboarding: Relayers can onboard users into token ecosystems without requiring users to acquire NEAR first. [near-meta-tx]
- Spam and storage protection: Contract authors cannot be economically attacked via unconstrained account creation. [near-storage-mgmt]
- Clean state cleanup: Unregistering an empty token balance refunds the storage deposit to the user. [near-storage-mgmt]

**Weaknesses:**
- Registration friction: New users often encounter unexpected errors when receiving tokens if the sender does not automatically cover the recipient's `storage_deposit`. [near-storage-mgmt]
- Dual-action transfers: Senders sending tokens to an unregistered account must attach both the token amount and the NEAR storage registration in a compound call. [near-storage-mgmt]

## What the lesson must show

1. Inspect a deployed NEP-141 token contract (`token.testnet`).
2. Attempt a token transfer to an unregistered recipient mailbox and observe the expected storage registration refusal.
3. Call `storage_deposit` (0.00125 NEAR) to register the recipient's mailbox.
4. Execute an `ft_transfer` now that storage is provisioned.
5. Demonstrate a gasless meta-transaction: the learner signs a transfer, a mock/testnet relayer pays the gas fee, and the token balances update while the learner's NEAR balance remains untouched.
