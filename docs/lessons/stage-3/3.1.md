# Lesson 3.1: Deploy a contract in one click

Issue: #19. Target time: 5 minutes. Chain access: testnet (practice account) or demo mode (DemoChain). Views: 2D and 3D, one shared state.

Topic: `3.1-topic.md` (the source of truth for what this lesson teaches).

## 1. Learning goals

1. Deploy a pre-compiled WebAssembly (`.wasm`) smart contract to a new sub-account.
2. Understand NEAR's storage staking model: locking 1 NEAR per 100 KB instead of paying ongoing rent.
3. See what a failing call does when a callback waits for it.
4. Observe how locked storage deposits are refunded to available balance when state is deleted.

## 2. Steps

Placeholders (`vars`): `{contract}` = the learner's contract account, `{codeBytes}` = size of the Wasm,
`{storageDeposit}` = NEAR locked for storage after the deploy,
`{refund}` = NEAR returned by the reset. All come from the chain, never from fixed numbers.

### Step 1: Hook (Code that lives on a name)

- **Caption:** Where do smart contracts live on NEAR? On an account name, as WebAssembly code.
- **Explain:** On Ethereum, deploying a contract gives you a new hex address. On NEAR, a contract lives on an account you control, often a **sub-account** like `{contract}`. Contracts compile to **WebAssembly** (Wasm), a standard binary code format browsers also run.
- **Scene:** Your mailbox, with a dashed sub-mailbox on its post labelled `{contract}`. A dashed scroll with a gear (the contract, not deployed) stands ready. No gate.

### Step 2: The sub-account and the Wasm bytecode

- **Caption:** Your contract gets its own sub-account, {contract}. Its code is {codeBytes} bytes of WebAssembly.
- **Explain:** Any named account can create sub-accounts, with no registrar. A hex (implicit) practice account is already 64 characters, the limit, so the lesson first gives it a short name, as in lesson 1.1. The counter was written by hand in Wasm text, so no Rust toolchain is needed. Every Wasm file starts with the bytes `00 61 73 6d` ("\0asm").
- **Scene:** The scroll unrolls: the first bytes of the real file, its size and the methods it exports. Picking the scroll unrolls it. Next is open.

### Step 3: Deploy and lock storage deposit

- **Caption:** Deploy the contract in one transaction. Watch {storageDeposit} NEAR lock into storage staking.
- **Explain:** One batch creates `{contract}`, sends it 0.05 NEAR and deploys the code. NEAR charges no rent. Instead, an account must keep **1 NEAR per 100 KB** it stores, locked. That is the **storage deposit**. The rest is its **available balance**, which it can spend.
- **Action:** Button **Deploy counter contract** (or pick the mailbox). The sub-mailbox becomes solid, the scroll mounts on it, and the balance gauge splits into locked and available. Gate opens when deployed.
- **Evidence:** `{ contractId, txHash }`.

### Step 4: Call the contract and read it back

- **Caption:** Click Increment to change the count. Then read it back with a second, free call.
- **Explain:** `increment` is a **change call**: a transaction that runs the Wasm and writes the count to the account's storage. That new record needs a few more bytes of storage deposit. `get_num` is a **view call**: it only reads, needs no transaction and costs you no gas.
- **Action:** Buttons **Increment** and **Read the count**. The scroll's gear turns, the count shows on it. Gate opens after at least one increment and a read that returns it.

### Step 5: A call that fails, and its callback

- **Caption:** Ask the counter to call its own fail method, with a callback that waits for the answer.
- **Explain:** `call_other` calls `fail`, which always stops with an error. A failed call changes nothing, but the gas is still spent. The **callback**, `on_other_done`, runs in a later block and is told the call failed. It writes "failed" to storage. NEAR does not undo the caller's work: the callback must handle it.
- **Action:** Button **Call fail with a callback**. Three receipts appear: `call_other` ✓, `fail` ✗, `on_other_done` ✓, each with the gas it burnt (the failed one too). The scene reads `last_result` ("failed") and the unchanged count. Gate opens when the effect is read back.

### Step 6: Delete state and reclaim your NEAR

- **Caption:** Clear the counter's state. The bytes it frees stop being locked: {refund} NEAR is available again.
- **Explain:** `reset` deletes the count and the last result. Storage staking is a deposit, not a fee: the locked NEAR for those bytes goes straight back to the account's available balance. The code itself stays, so its deposit stays locked.
- **Action:** Button **Reset and clear state**. The count drops to zero and the gauge moves back towards available. Gate opens when the storage shrank.

### Step 7: Quick check (summary page)

- **Caption:** Three quick questions on WebAssembly, sub-accounts and storage staking.
- **Action:** Check (section 3).

### Step 8: Honest take

- **Caption:** Honest take: storage staking, Wasm and upgrades, compared with Ethereum.
- **Gate:** none. The original script gated it on the deploy; that gate was removed on purpose, because the learner cannot reach this step without passing the gated steps 3 to 6 (and the check) first.

## 3. Check

**Q1. How is data storage paid for on NEAR?**
- A. By locking a refundable deposit of 1 NEAR per 100 KB of data stored. **(correct)**
- B. By paying a monthly fee to the network. *Wrong: there is no rent. The account keeps NEAR locked while the data exists.*
- C. Storage is free and unlimited. *Wrong: every stored byte needs locked NEAR.*

**Q2. What happens to your locked storage NEAR when you delete stored data?**
- A. It is unlocked and returned to your available balance. **(correct)**
- B. It is burned and lost forever. *Wrong: storage deposits are refundable.*
- C. It is sent to the validator as a bonus. *Wrong: it never leaves your account.*

**Q3. What code format do NEAR smart contracts compile down to?**
- A. Standard WebAssembly (Wasm). **(correct)**
- B. EVM bytecode. *Wrong: that is Ethereum's format. NEAR runs Wasm.*
- C. Python scripts. *Wrong: contracts compile to Wasm binaries.*

## 4. Honest take

The code (`Scene.tsx`) uses this text word for word.

**Strengths:**
- **Storage pays its way.** Every stored byte needs locked NEAR, and deleting data gives it back, so cleaning up is rewarded. On Ethereum you pay once to store and the network keeps it forever. [near-storage] [eth-storage]
- **Standard WebAssembly.** Write contracts in Rust or JavaScript; both compile to Wasm. This lesson's counter was written by hand in Wasm text, with no toolchain at all. [near-contracts] [repo]
- **Contracts live under your name.** counter.you.testnet is made by you, in the same batch as the deploy, with no registrar. [near-account-id] [near-anatomy]
- **Upgrade in place.** Deploy new code to the same account and it keeps its name and its stored state. Ethereum code cannot change, so upgrades need a proxy contract in front. [near-upgrade] [eth-upgrade]

**Weaknesses:**
- **The deposit comes first.** A 200 KB contract locks 2 NEAR before anyone uses it, which can surprise new builders. [near-storage]
- **LackBalanceForState.** If an account cannot cover the deposit for new data, the transaction fails until someone tops it up. Apps that store user data must charge users for storage or pay it themselves. [near-storage]
- **Upgradable by default.** Anyone holding a full-access key on the contract account can replace the code. Check that a contract's account has no full-access keys before you trust it. [near-upgrade]
- **No automatic rollback across calls.** When a called method fails, the caller's changes stay. Only a callback, written with care, can undo them. [near-cross-contract]

Compared with: **Ethereum** (one-time `SSTORE` gas fee, state stored forever, little reason to clean up; contract code cannot change, upgrades go through proxy contracts). [eth-storage] [eth-upgrade]

## 5. Demo-mode data

- Contract: `counter.<name>.testnet`, where `<name>` is the practice account if it is named, otherwise a fresh `bon-<random>.testnet` the lesson creates first.
- Code: the real `contracts/counter/counter.wasm` (about 2.1 KB), the same bytes as on testnet. DemoChain runs its JavaScript twin (matched by the code's hash) and counts every byte for storage.
- Contract account funding: 0.05 NEAR. Storage deposit after deploy: about 0.023 NEAR.
- Count: 0 → 1 per Increment. The callback records "failed". Reset frees the two records.
