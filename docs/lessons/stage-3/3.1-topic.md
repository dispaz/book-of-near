# Topic 3.1: Deploying WebAssembly contracts and State Storage Staking

## In one sentence

On NEAR, smart contracts compile to standard WebAssembly (Wasm) and deploy to human-readable sub-accounts, where on-chain storage is paid for by locking NEAR tokens (storage staking) that are refunded whenever data is deleted.

## The problem it solves

On blockchains like Ethereum, users pay a one-time gas fee to write data to state (`SSTORE`), but nodes must store that data forever for free, creating permanent "state bloat". Alternatively, traditional cloud systems charge recurring monthly subscription rents. NEAR solves this with state staking: you lock a refundable deposit proportional to the bytes you store. [near-storage] [eth-state-bloat]

## How it works on NEAR

**Standard WebAssembly (Wasm) Runtime.**
- NEAR smart contracts run inside a high-performance WebAssembly virtual machine (`near-vm`). [near-contracts]
- Developers write smart contracts in Rust (using `near-sdk-rs`) or JavaScript/TypeScript (using `near-sdk-js`). Both compile down to standard `.wasm` bytecode binaries. [near-contracts]

**Deploying to Sub-accounts.**
- Any account `alice.testnet` can permissionlessly create a sub-account like `counter.alice.testnet` without any central registrar approval. [near-account-id]
- A single batch transaction (Topic 1.3) can create the sub-account, transfer initial NEAR for storage, and deploy the `.wasm` binary in one atomic step. [near-anatomy]

**Storage Staking (State Staking).**
- Storing data on NEAR (contract bytecode, key-value state, account records) requires locking native NEAR at a fixed protocol rate: **1 NEAR per 100 KB** (approx. 0.00001 NEAR per byte, or 100,000 NEAR per 10 GB). [near-storage]
- This locked balance is not burned or paid as rent; it remains in the account as **storage staking deposit**. [near-storage]
- **Refundable:** If a contract cleans up data (deletes a record or clears storage), the locked NEAR is instantly unlocked and returns to the account's available liquid balance. [near-storage]
- **`LackBalanceForState`:** If an account's available balance is too low to cover the storage requirement of new records or code, the transaction reverts with a `LackBalanceForState` error. [near-storage] [spike-2]

## Words to know

- **WebAssembly (Wasm):** A high-performance portable binary code format supported by modern browsers and the NEAR runtime.
- **Sub-account:** An account created directly under a parent name (e.g. `app.alice.testnet`), requiring no registrar.
- **Storage staking:** The protocol requirement to hold locked NEAR tokens proportional to on-chain bytes stored.
- **Available balance:** Liquid NEAR that can be spent on gas or transferred, excluding funds locked in storage staking.
- **`LackBalanceForState`:** The protocol error returned when an operation attempts to store data without enough locked balance.

## Common misunderstandings

- **"Storage staking is a recurring monthly fee."** No. It is a one-time refundable security deposit. When you delete the stored data, 100% of the locked NEAR becomes spendable again. [near-storage]
- **"Deploying code requires a specialized command-line toolchain."** While developer tools exist (`near-cli`), deployment is fundamentally a standard transaction action (`DeployContract`) that can be executed from a web browser. [near-anatomy]
- **"Contract state lives in a separate database from the account."** Contract bytecode and key-value state are bound directly to the account that holds them. [near-contracts]

## Compared with Ethereum

- **Ethereum:** Pay a one-time gas fee (`SSTORE`) to store data forever. There is no economic incentive to ever delete obsolete data, resulting in uncontrolled global state bloat. Code runs on a custom EVM bytecode architecture. [eth-storage]
- **NEAR:** Requires a deposit of 1 NEAR per 100 KB. Deleting data refunds the deposit, encouraging efficient storage hygiene. Code runs on standard Wasm. [near-storage]

## Strengths and weaknesses (feeds the Honest take)

**Strengths:**
- Sustainable economics: Solves the blockchain state bloat problem through refundable storage staking deposits. [near-storage]
- Language flexibility: Standard WebAssembly engine supports Rust and JavaScript. [near-contracts]
- Frictionless deployment: Hierarchical sub-accounts allow developers to isolate contracts cleanly without registrar intervention. [near-account-id]

**Weaknesses:**
- Upfront capital requirement: Deploying a large contract (e.g., 200 KB) requires locking 2 NEAR upfront, which can be a friction point for new developers. [near-storage]
- State growth can lock funds: Applications storing user data must either pay storage on behalf of users or enforce storage deposits via NEP-145 (Topic 3.2). [near-storage]

## What the lesson must show

1. Inspect a pre-compiled lightweight counter Wasm contract (~10 KB).
2. Create a sub-account `counter.<learner>.testnet` and calculate storage cost (~0.1 NEAR).
3. Deploy the contract using `DeployContract` action and call an initialization method.
4. Read contract state and increment the counter.
5. Demonstrate state staking: watch available balance vs locked storage balance shift as state expands, and see locked funds return when state is cleared.
