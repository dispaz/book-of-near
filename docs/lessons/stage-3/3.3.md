# Lesson 3.3: Race the RPC nodes

Issue: #21. Target time: 4 minutes. Chain access: read-only (live testnet RPCs) or demo mode. Views: 2D and 3D, one shared state.

Topic: `3.3-topic.md` (the source of truth for what this lesson teaches).

## 1. Learning goals

1. Compare real-time query latency across multiple independent RPC providers.
2. Observe how client libraries race requests or maintain fallback lists for resilience.
3. Simulate an RPC provider outage and watch automatic failover keep the application online.

## 2. Steps

### Step 1: Hook (The window into the blockchain)

- **Caption:** Your wallet doesn't connect to every validator directly. It talks through an RPC node.
- **Explain:** A **Remote Procedure Call (RPC)** node is your application's gateway into the blockchain. If your dApp relies on a single provider and that provider goes down, your users are completely locked out—even if the blockchain is running perfectly.
- **Scene:** Your learner mailbox with three post-office counter windows in the background representing different providers: FastNEAR, NEAR Foundation, and DRPC. No gate.

### Step 2: Race the providers

- **Caption:** Send the same block query to three providers at the exact same instant.
- **Explain:** Client libraries can dispatch simultaneous requests. The fastest response updates your UI; slower replies are discarded.
- **Action:** Button **Race the nodes**. Stopwatch timers tick beside each counter window. FastNEAR responds in ~140ms, Foundation in ~220ms, DRPC in ~290ms. Gate opens when the race finishes.
- **Evidence:** `{ fastestRpc: "FastNEAR", latencyMs: 140 }`.

### Step 3: Simulate an RPC outage

- **Caption:** What happens when the fastest provider crashes or rate-limits your IP?
- **Explain:** During high-traffic events, public endpoints can return `429 Too Many Requests` or `503 Service Unavailable`. Resilient apps use **failover lists** (`fallbackRpcUrls`).
- **Action:** Toggle **Disable FastNEAR**. FastNEAR's counter window goes dark with a red "Offline" sign. Next is open.

### Step 4: Automatic failover in action

- **Caption:** Send a new query. The client catches the error and instantly switches to the backup node.
- **Explain:** The request hits FastNEAR, detects the outage, and immediately reroutes to the NEAR Foundation endpoint. The user notices only a minor 80ms latency change.
- **Action:** Button **Send query via failover**. The query automatically routes through the NEAR Foundation window and returns block data successfully. Gate opens on success.

### Step 5: Archival vs. standard nodes

- **Caption:** Ask for Block #1,000,000 from 2 years ago. Standard nodes say "Not Found".
- **Explain:** Standard RPC nodes only store the last **5 epochs** (~2.5 days) of state history to save disk space. To read older transactions or blocks, your client must query an **archival node**.
- **Action:** Button **Query historical block**. Watch the standard node return 404, while the archival node returns the genesis-era block data. Gate opens.

### Step 6: Quick check (summary page)

- **Caption:** Three questions on RPC nodes, failover, and archival data.
- **Action:** Check (section 3).

### Step 7: Honest take

- **Caption:** Honest take: Decentralized RPC infrastructure vs. centralized infrastructure monopolies.
- **Gate:** Gated until failover query succeeds in step 4.

## 3. Check

**Q1. Why should a dApp or wallet never rely on a single RPC endpoint?**
- A. If that single provider experiences an outage, the entire dApp goes dark for users. **(correct)**
- B. Because single RPC nodes charge 100 NEAR per query. *Wrong: most public RPC endpoints are free.*
- C. Because the blockchain stops producing blocks. *Wrong: RPC nodes do not produce consensus blocks.*

**Q2. What is the difference between a standard RPC node and an archival node?**
- A. Standard nodes only retain the last 5 epochs of state; archival nodes store the entire history since genesis. **(correct)**
- B. Archival nodes are only accessible via paper mail. *Wrong: archival nodes are standard HTTP/JSON-RPC servers.*
- C. Standard nodes cannot process token transfers. *Wrong: standard nodes process all modern transactions.*

**Q3. How does client-side failover handle an RPC node failure?**
- A. It automatically retries the request against the next available provider in its fallback list. **(correct)**
- B. It formats the user's hard drive to prevent data leaks. *Wrong: client libraries simply switch network endpoints.*
- C. It forces the user to buy a new laptop. *Wrong: failover happens seamlessly in software.*

## 4. Honest take

**Strengths:**
- **Open public access:** Free high-performance providers like FastNEAR provide open CORS (`*`), allowing browser dApps to connect directly without paid API keys. [spike-3]
- **Transparent failover:** Libraries like `near-kit` natively support array fallback lists (`fallbackRpcUrls`). [spike-3]

**Weaknesses:**
- **Public endpoint deprecations:** Public nodes from third parties (e.g. Lava, Ankr) have historically been shut down or rate-limited without warning, requiring continuous list maintenance. [spike-3]
- **State latency drift:** During rapid shard re-sharding, different providers may have slight block synchronization differences of a few hundred milliseconds. [near-rpc]

Compared with: **Ethereum** (heavy historical reliance on Infura and Alchemy monopolies, where single-provider outages have taken down major DeFi frontends).
