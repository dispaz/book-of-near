# Lesson 1.3: Inside a NEAR transaction

Issue: #16. Target time: 6 minutes. Chain access: testnet (real transactions from a workshop account the lesson makes) or demo mode (DemoChain, same rules). Views: 2D and 3D, one shared state. Everything goes through the `Chain` interface (`docs/chain.md`); no interface change was needed (`buildTransaction`, `signTransaction` and `sendSignedTransaction` already exist).

Scope (owner, 2 Nov 2026): lesson 0.3 already shows the nonce and the recent block hash and says what they are. This lesson does not define them again. It adds the new part: the learner re-sends an old signed transaction from earlier in this lesson and sees that the chain will not run it again (its nonce is used), which shows **why** the nonce and the block hash exist (replay protection and expiry). The main topic stays: several actions in one transaction, one fails, all roll back.

Facts come from [near-anatomy], [near-lifecycle] and `docs/spikes-seed.md` (Result log, spike 1: `testnet.create_account` with a deposit creates and funds a named account). Anything else is marked (unverified).

## 1. Learning goals

1. Name the parts of a NEAR transaction: signer, receiver, actions, nonce, block hash, signature.
2. Put several actions in one transaction, in order, and know they all go to one receiver.
3. See that when one action fails, every action of that transaction is undone, and the fee is still paid.
4. See that a copy of an old signed transaction does not run again, and say why (nonce, block hash).

## 2. Steps

### Step 1: Hook

- **Caption:** One NEAR transaction can carry several actions. If one of them fails, what happens to the others?
- **Explain:** An **action** is one thing a transaction asks the chain to do: create an account, send NEAR, add a key, call a contract. A transaction carries a list of actions. In this lesson you stack three, then break one on purpose.
- **Scene:** A transaction drawn as a card with empty action slots. No action. Next is open.

### Step 2: Open a transaction

- **Caption:** First make {parent}, an account to work in. Then look inside the transaction that made it. (`{parent}` is the lesson's workshop account; default text "a workshop account".)
- **Explain:** Every transaction has the same parts. The **signer** signs it and pays the fee. The **receiver** is the one account its actions apply to. Then come the actions. The nonce and the block hash you met in lesson 0.3. Later in this lesson you see why they are there.
- **Action:** Button **Make the workshop account**. It calls `create_account` on the `testnet` registrar from the practice account with 0.1 NEAR, as in lesson 1.1. The new account gets the practice account's own public key (the same key on two accounts is allowed; each account keeps its own nonce for it), so the app can sign for it after a reload. On load, the lesson first looks for a workshop account from an earlier visit that holds this key and reuses it (no new deposit). The scene then shows the transaction's fields with one-line labels: nonce ("the key's counter, +1 each time"), block hash ("a recent block: sets a deadline"). Gate opens when the account exists. If the practice account is short of NEAR, the lesson says so and offers demo mode.

### Step 3: Build a batch

- **Caption:** Stack three actions for {sub}, in order, and send them as one transaction.
- **Explain:** All the actions in one transaction go to one receiver, here the new account {sub}. They run in the order you list them. {parent} signs once and pays one fee. Order matters: an account must exist before it can get NEAR or keys.
- **Action:** A builder. Name box for the new sub-account (the part before `.{parent}`, default `shop`), amount box (0.01 to 0.05 NEAR, default 0.02). Buttons add **Create account**, **Send NEAR**, **Add a key**; each row can move up, move down or be removed. **Send the batch** builds, signs and sends it, then shows each action's result and the new account. A wrong order fails like any other failure (step 4) and the learner tries again. Gate opens after a batch with all three kinds of action succeeds. Reports `sub`, `amount` and `nonce` with `setVars`. Evidence: the batch's transaction id.

### Step 4: Break it

- **Caption:** Now break it. Send a batch for {failsub} that adds the same key twice.
- **Explain:** Adding a key the account already has fails. When an action fails, the chain undoes every action of that transaction, even the ones that already ran. {failsub} is not created, {comesback}. (`{comesback}` reads "and the NEAR sent to it (0.02 NEAR) comes back", or "and no NEAR was sent to it, so none moves" when the batch has no Send row.) The fee for the work done is still paid.
- **Action:** The builder again, prefilled with a new name (`{sub label}2`) and the batch plus **Add that key again**. After sending, each action shows "ran, then undone", "failed" or "never ran"; the app asks the chain whether {failsub} exists (it does not) and shows the workshop account's balance before and after (only the fee is gone; "the NEAR it was sent came back" shows only when the batch had Send rows). Gate opens after a failed batch that undid at least one action, on a name that did not exist before; a failure at the first action, or on an existing account, undoes nothing and keeps the gate shut. A storage shortfall (`LackBalanceForState`, which nearcore reports with no action index) shows as "all ran, then undone".

### Step 5: Send it again

- **Caption:** Your first batch had nonce {nonce}. Send that same signed transaction again, unchanged.
- **Explain:** Anyone who sees a signed transaction could send a copy. The nonce stops that: each key's nonce only goes up, so a copy with a used nonce never runs again and costs nothing. A node simply answers with the first result. The block hash adds a deadline: once that block is too old, even an unused transaction expires.
- **Action:** Buttons **Re-send the batch that worked** and **Re-send the batch that failed**. Each shows "Not run again", the chain's reason when it gives one (`InvalidNonce`), the transaction's nonce and the key's nonce now. A failed transaction used its nonce too. Honest framing: a real node answers an exact copy with its earlier result; TestnetChain checks the nonce first and reports `InvalidNonce`, so the learner sees why. Gate opens when one copy did not run.
- **Expiry numbers:** NEAR's docs give 86,400 blocks as an example validity period, about 14 hours at 600 ms a block [near-lifecycle]. Testnet's real value comes from `protocol_config` and is **not checked** here, so the lesson says "a set number of blocks" and does not demonstrate expiry.

## 3. Glossary terms introduced

- **Action:** one thing a transaction asks the chain to do (create an account, send NEAR, add a key, deploy, call).
- **Signer:** the account that signs the transaction and pays its fee.
- **Receiver:** the one account a transaction's actions apply to.
- **Batch:** a transaction with several actions. Not a separate NEAR term; used here for clarity.
- **Roll back:** undo every change of a failed transaction's actions.
- **Replay:** sending a copy of an old signed transaction again.
- From 0.3, not defined again: **nonce**, **block hash**.

## 4. Check

**Q1. A transaction creates an account, sends it NEAR, then adds a key the account already has. What is left afterwards?**
- A. No new account. The NEAR came back; only the fee is spent. **(correct)**
- B. The account exists with the NEAR, but without the key. *Wrong: the actions of one transaction stand or fall together, so the first two were undone.*
- C. Nothing at all, not even the fee. *Wrong: the work up to the failure was done, so the fee is still paid.*

**Q2. Why did your old transaction not run again when you sent it a second time?**
- A. Its nonce was already used by that key. **(correct)**
- B. Its signature wore out. *Wrong: a signature does not wear out; what counts is that its nonce was used.*
- C. Someone else had sent it first. *Wrong: nobody else sent it; your own first send used up the nonce.*

**Q3. Can one NEAR transaction act on two different accounts?**
- A. No. All its actions go to its one receiver. **(correct)**
- B. Yes, each action can name its own account. *Wrong: a transaction has exactly one receiver.*

## 5. Honest take

Comparison: Ethereum.

**Strengths**
- **Batching is built in.** A NEAR transaction is a list of actions. They run in the order given, and if one fails none of them take effect. [near-anatomy]
- **Account changes are plain actions.** Creating an account, sending NEAR and adding a key need no contract. [near-anatomy]
- **Two guards against copies.** The nonce makes a used transaction worthless, and the block hash gives every transaction a deadline. [near-anatomy] [near-lifecycle]

**Weaknesses**
- **One receiver per transaction.** To act on two accounts you need two transactions, or a contract that calls others. [near-anatomy]
- **All-or-nothing covers one account's actions only.** When a contract calls another contract, that call runs later, in another block, and if it fails the earlier work stays done (Stage 2). [near-lifecycle]
- **A failed transaction still costs a fee.** [near-lifecycle]
- **The deadline cuts both ways.** A transaction signed now must be sent within the validity window, which makes slow signing setups harder. The window is a set number of blocks (86,400 in the docs' example, about 14 hours). [near-lifecycle]
- **Ethereum is closing the gap.** A plain Ethereum transaction has one recipient and one call. EIP-7702, part of the Pectra upgrade, lets a plain account borrow a contract's code, so it can batch calls such as approve and transferFrom when its wallet supports it. [eth-tx] [eth-7702]

## 6. Demo-mode data

- Practice account and 5 NEAR as in 0.3. Workshop account `tx-<first six letters or digits of the practice id>.testnet` (a suffix `-2`, `-3`, … if taken), made through `createNamedAccount` with 0.1 NEAR and the practice account's public key (kept by the chain across reloads). A later visit reuses it when it holds that key.
- Batch: signer the workshop account, receiver `<label>.<workshop>`, actions `CreateAccount`, `Transfer(amount)`, `AddKey(fresh key, full access)`. "Add that key again" repeats the last `AddKey`'s key, so it fails with `AddKeyAlreadyExists` (nearcore name, mapped by both chains).
- The batch is sent as `buildTransaction` → `signTransaction` → `sendSignedTransaction`, and the signed object is kept, so the replay sends exactly the same bytes.
- Replay: `sendSignedTransaction(oldSigned)`. DemoChain refuses with `InvalidNonce`. TestnetChain checks the key's nonce first and refuses with `InvalidNonce` (real nodes answer a re-sent transaction with its old result instead of running it again; `docs/chain.md`, mapping notes). Nothing is charged.
- Rollback: DemoChain restores the receiver's state and refunds deposits in a `system` receipt a block later. On testnet the same is expected [near-lifecycle] but the exact refund timing is **not checked** for this lesson.
- Amounts: workshop deposit 0.1 NEAR (enough for its storage, about 0.002 NEAR by our estimate (unverified), and several batches of up to 0.05 NEAR; a failed batch gets its NEAR back); learner amount 0.01 to 0.05 NEAR, default 0.02. Numbers on screen (fee, balances) come from the chain, not from this note.
