# Topic 1.3: Inside a NEAR transaction (actions, roll-back, replay)

The source of truth for lesson 1.3. The lesson script (`1.3.md`) and the code may only teach what this
file says. Facts carry a source tag; anything else is marked (unverified).

## In one sentence

A NEAR transaction is a signed list of actions for one receiver: they run in order, all of them or
none of them, and a used nonce means the same transaction can never run twice.

## The problem it solves

- **Doing several things at once.** Making an account, funding it and giving it a key are three steps.
  If the third fails, you don't want a half-made account. [near-anatomy]
- **Copies.** A signed transaction is public once sent. Without a guard, anyone could send the copy
  again and repeat the payment. [near-anatomy]

## How it works on NEAR

**Parts of a transaction.** [near-anatomy]

| Part | Meaning |
| --- | --- |
| Signer | The account that signs and pays the fee. |
| Receiver | The one account all the actions apply to. |
| Actions | The list of things to do, in order. |
| Nonce | A counter for the signing key; each transaction must use a higher one (from 0.3). |
| Block hash | A recent block; sets a deadline (from 0.3). |
| Signature | Proof the signer's key approved exactly these bytes. |

**Actions.** Create an account, send NEAR, add or delete a key, deploy code, call a contract. Account
changes need no contract. [near-anatomy]

**One receiver.** Every action in a transaction goes to the same account. [near-anatomy]

**All or nothing.** "If any of the actions fails, the transaction is discarded and none of the actions
take effect." The fee for the work done is still paid. [near-anatomy] [near-lifecycle]

**Limit of all-or-nothing.** It covers one receipt (one account's actions). When a contract calls
another contract, that call runs later, and if it fails the earlier work stays done (Stage 2).
[near-lifecycle]

**No replays.** Each key's nonce only goes up, so a copy with a used nonce is not run again. The block
hash adds a deadline: once that block is too old, even an unused transaction expires. The docs' example
window is 86,400 blocks, about 14 hours at 600 ms a block; testnet's real value is unverified.
[near-anatomy] [near-lifecycle]

## Words to know

- **Action:** one thing a transaction asks the chain to do.
- **Signer / receiver:** who signs and pays / which account the actions apply to.
- **Batch:** a transaction with several actions (our word, not a NEAR term).
- **Roll back:** undo every change made by a failed transaction's actions.
- **Replay:** sending a copy of an old signed transaction again.

## Common misunderstandings

- **"The actions before the failure still happened."** Within one transaction, no: all are undone. [near-anatomy]
- **"A failed transaction is free."** No, the fee for work done is paid. [near-lifecycle]
- **"One transaction can pay two people."** Not directly: one receiver per transaction. [near-anatomy]
- **"A signature can be reused later."** The nonce is used up, so the copy does not run.

## Compared with Ethereum

A plain Ethereum transaction has one recipient and one call. EIP-7702 (Pectra) lets a plain account
borrow contract code so it can batch calls when its wallet supports it. [eth-tx] [eth-7702]

## Strengths and weaknesses (feeds the Honest take)

See `1.3.md` section 5: batching built in; account changes are plain actions; two guards against
copies. Weaknesses: one receiver; all-or-nothing stops at cross-contract calls; failed transactions
still cost; the deadline makes slow signing setups harder; Ethereum is closing the gap.

## What the lesson must show

1. A transaction as a container of actions.
2. Its parts, on a real transaction.
3. A batch of three actions succeeding.
4. A batch failing on its last action, and the earlier actions being undone (fee still paid).
5. Re-sending an old signed transaction and seeing it not run again.
