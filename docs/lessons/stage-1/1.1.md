# Lesson 1.1: Claim your name

Issue: #14. Target time: 4 minutes. Chain access: testnet (a real `.testnet` account made from the practice account) or demo mode (the same call on DemoChain). Views: 2D and 3D, one shared state.

Facts come from `docs/spikes-seed.md` (Result log, spike 1: `testnet.create_account` with a deposit creates and funds a named account in one call; a transfer to a hex id makes an implicit account) and the NEAR account id page [near-account-id]. Anything else is marked (unverified).

## 1. Learning goals

1. Say what an account id is, and the rules a NEAR name must follow.
2. Create a named testnet account and see its details (id, balance, key).
3. Explain how a named account differs from a plain hex account, and how that compares with Ethereum's naming service.

## 2. Steps

### Step 1: A hex address

- **Caption:** Most chains give you an address like 7f3a9c0d... Nobody can say it out loud. NEAR lets an account have a name.
- **Explain:** An **account id** is the address of an account. Your practice account has a long hex one: 64 characters made from its public key. That is called an **implicit account**. It works, but nobody can remember it.
- **Scene:** The practice account mailbox with its hex id (shortened, full id on hover). No action. Next is open.

### Step 2: A name is an address

- **Caption:** A NEAR account can have a readable id such as ana.testnet. The name is the account's address.
- **Explain:** A **named account** has an id you choose. Rules: 2 to 64 characters; lowercase letters, digits and the marks - _ and . ; a mark must sit between two letters or digits. On testnet, a **registrar** (a contract named `testnet`) creates names that end in `.testnet`. You ask it, attach a little NEAR and give it a public key.
- **Scene:** The practice account, the `testnet` registrar (a contract scroll) and an empty dashed mailbox for the new account. No action.

### Step 3: Pick a name

- **Caption:** Type a name. The app checks, as you type, whether it is free.
- **Explain:** Each id exists once. The app asks the chain whether the account exists. Free means nobody has it yet. It is first come, first served.
- **Action:** Text box for the part before `.testnet`. Live feedback: a rule problem, "taken" or "free". Next unlocks when the name is valid and free. Reports `name` with `setVars`.
- **Demo data:** `book-of-near.testnet` exists in demo mode, so it shows "taken".

### Step 4: Create it

- **Caption:** Ask the registrar to create {name} and send it 0.1 NEAR from your practice account.
- **Explain:** One transaction calls `create_account` on `testnet` with your name, a new public key and a deposit. The registrar makes the account, funds it and adds your key as a **full-access key**, a key that can do anything with the account. The app keeps the matching private key in this browser (testnet only; never reuse it anywhere else).
- **Action:** Button "Create {name}". Shows the transaction id, the block, the fee paid and the new balance. Next unlocks when the account exists. Evidence: `{ accountId, txHash }`.

### Step 5: Name or hex?

- **Caption:** {name} and a hex id can both be NEAR accounts. The name is easier to read, share and check.
- **Explain:** The same public key could also be an implicit account with a hex id. That account would not exist until someone sent it NEAR. A named account exists because the registrar made it. The name belongs to the account, not to a key: keys can be added and removed later (Lesson 1.2).
- **Scene:** Two mailboxes side by side: `{name}` (exists, balance, its key) and the hex id of the same key (dashed: not created). Testnet shows a NearBlocks link: `https://testnet.nearblocks.io/address/<id>`.

## 3. Check

**Q1. What is an account id?**
- A. The address of an account: a name or a hex string. **(correct)**
- B. The secret that signs transactions. *Wrong: that is the private key.*
- C. A fee paid when you create an account. *Wrong: fees are paid in NEAR; an id is only an address.*

**Q2. How did your name get created?**
- A. A transaction asked the `testnet` registrar contract to create it and fund it. **(correct)**
- B. The app wrote it into its own database. *Wrong: the account lives on the chain, not in the app.*
- C. It existed already and the app only read it. *Wrong: the app checked that it was free first.*

**Q3. Which id is valid?**
- A. ana-1.testnet **(correct)**
- B. Ana.testnet *Wrong: only lowercase letters are allowed.*
- C. ana..testnet *Wrong: a mark must sit between two letters or digits.*

## 4. Honest take (compared with Ethereum)

**Strengths**
- Names are accounts. A NEAR account id can be readable, and it is part of the protocol, so the same id works in every app. [near-account-id]
- One transaction creates the account, funds it and adds its key. (Spike 1, real testnet transaction.)
- The name belongs to the account, not to a key, so keys can change without changing the name. [near-account-id]

**Weaknesses**
- Names are first come, first served on a shared registrar. A taken name is gone, and squatting is possible. (Mainnet registrar rules unverified.)
- A name costs NEAR to create: the deposit, plus a fee that was about 0.0075 NEAR on testnet. Why it is higher than gas times price is unverified.
- Ethereum has no names in the protocol: an address is hex, and ENS is a separate service on top. That is a trade: ENS is optional and independent; a NEAR name is built in but lives in a registrar's tree. [ens] (Details unverified.)
- Hex accounts still exist on NEAR, so wallets and apps must handle both kinds of id.
