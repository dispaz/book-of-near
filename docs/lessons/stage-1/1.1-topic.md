# Topic 1.1: Account ids (named and implicit accounts)

The source of truth for lesson 1.1. The lesson script (`1.1.md`) and the code may only teach what this
file says. Facts carry a source tag; anything else is marked (unverified).

## In one sentence

On NEAR an account's address can be a readable name such as `ana.testnet`, and that name is the
account itself, not a nickname that points somewhere else.

## The problem it solves

Addresses on most chains are long hex strings made from a public key. Nobody can say one out loud,
and a typo sends money to the wrong place. [near-account-id]

## How it works on NEAR

**Two kinds of account id.** [near-account-id]

| Kind | Looks like | How it comes to exist |
| --- | --- | --- |
| **Implicit account** | 64 hex characters, made from a public key | When someone sends NEAR to that id. |
| **Named account** | `ana.testnet`, `shop.ana.testnet` | Created by a transaction, usually through a registrar. |

**Name rules.** 2 to 64 characters; lowercase letters, digits and `-` `_` `.`; a mark must sit between
two letters or digits. [near-account-id]

**Who hands out names.** A top-level name like `ana.testnet` is made by the account `testnet`, a
**registrar** contract. You call its `create_account` with the new name, a public key and some NEAR. One
transaction creates the account, funds it and adds the key as a full-access key. (Spike 1,
`docs/spikes-seed.md`.)

**First come, first served.** Each id exists once. If it exists, it is taken. [near-account-id]

**The name belongs to the account, not to a key.** Keys can be added and removed later; the name stays
(topic 1.2). [near-account-id]

## Words to know

- **Account id:** the address of an account. A name or a hex string.
- **Implicit account:** an account whose id is the hex form of a public key.
- **Named account:** an account with an id you choose.
- **Registrar:** the contract that creates names under it (here `testnet`).
- **Full-access key:** a key that can do anything on its account (defined fully in 1.2).

## Common misunderstandings

- **"The name is a label on top of a hex address."** No, the name *is* the address. There is no hidden
  hex account behind it. [near-account-id]
- **"The app saved my name."** The account lives on the chain; the app only sent the transaction.
- **"My name is my key."** Keys can change; the name stays. [near-account-id]

## Compared with Ethereum

An Ethereum address is always hex. Names come from ENS, a separate service on top, which maps a name
to an address. [ens] (Comparison details beyond that are unverified.)

## Strengths and weaknesses (feeds the Honest take)

Strengths: readable ids built into the protocol; one transaction to create, fund and key an account;
the name outlives any key. Weaknesses: first come, first served (squatting possible); a name costs NEAR
to create; apps must handle both named and hex ids. See `1.1.md` section 4 for tags.
