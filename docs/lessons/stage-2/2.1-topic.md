## In one sentence

NEAR scales by splitting its single state and computation across parallel shards (Nightshade), where each block contains one chunk per shard and validators verify chunks statelessly using cryptographic state witnesses.

## The problem it solves

On traditional monolithic blockchains (like early Ethereum or Bitcoin), every validator node must process every transaction and store the entire global state. As user activity grows, nodes hit hardware limits, leading to high fees, network congestion, and rising barriers to node participation. [near-sharding]

## How it works on NEAR

**Nightshade architecture.** NEAR models the blockchain as a single logical chain, but internally partitions both state and computation into multiple parallel tracks called **shards**. [near-sharding]

**Blocks and chunks.**
- A **block** is produced roughly every 1–1.5 seconds by a block producer. [near-sharding]
- Instead of packing all network transactions directly into a block, each shard produces a **chunk** (a shard-specific slice of transactions and receipts). [near-nomicon]
- A block is essentially an aggregation containing one chunk header from each active shard. [near-nomicon]

**Dynamic shard assignment (boundary accounts).**
- An account lives on exactly one shard determined deterministically by sorting account IDs against a list of **boundary accounts** defined in the protocol configuration (`EXPERIMENTAL_protocol_config` / `shard_layout.V3`). [spike-3]
- When account IDs are lexicographically compared to boundary accounts, `shard_id = shard_ids[count(boundary_accounts <= account_id)]`. [spike-3]
- On testnet today, there are 10 shards with non-contiguous IDs (`[10, 11, 1, 12, 13, 9, 6, 7, 4, 5]`); because layouts change during resharding, shard IDs must always be queried at runtime rather than hard-coded. [spike-3]

**Transaction lifecycle across shards.**
1. A transaction is initiated and signed by an account. It executes on the **signer's shard** in that shard's chunk. [near-exec]
2. If the receiver lives on another shard, execution on the signer's shard generates an **Action Receipt**. [near-exec]
3. The receipt is routed across the network to the receiver's shard and included in that shard's chunk in a subsequent block. [near-exec]
4. Unused gas triggers a **Refund Receipt**, which travels back to the signer's shard in another subsequent block. [near-exec]

**Stateless Validation (Nightshade 2.0).**
- In traditional sharding, a validator assigned to a shard had to download and store the complete state of that shard to validate chunks. [near-stateless]
- Under Stateless Validation, chunk producers bundle execution state data and Merkle proofs into a **state witness**. [near-stateless]
- Shard validators receive the chunk along with its state witness and can verify state transitions without holding the entire shard state locally on disk. Active state portions can be held in fast memory. [near-stateless]

## Words to know

- **Shard:** A partition of accounts, contracts, and state on NEAR.
- **Chunk:** The package of transactions and receipts executed for a single shard within a block.
- **Block:** The unified network record containing chunk headers from all shards.
- **Boundary account:** The account ID thresholds that divide the namespace into shards.
- **State witness:** A cryptographic proof bundled with state data allowing stateless verification of a chunk.
- **Doomslug:** NEAR's consensus mechanism delivering single-round finality (~1-2 seconds) under normal network conditions.

## Common misunderstandings

- **"Different shards are separate blockchains."** No. To users and developers, NEAR appears as one seamless blockchain with one unified address space. Cross-shard routing is handled by the protocol. [near-sharding]
- **"Transactions across shards execute in a single block."** No. Each receipt hop between shards requires a block boundary, meaning cross-shard calls take 2 or more blocks. [near-exec]
- **"Transaction status in RPC tells you the shard ID."** No. The RPC transaction status omits the shard ID; clients must compute it from protocol configuration and account boundaries. [spike-3]

## Compared with Ethereum and Solana

- **Ethereum:** Sharded execution chains were removed from Ethereum's roadmap in favor of layer-2 rollups (Danksharding / proto-danksharding EIP-4844 for rollup blob data). Rollups require cross-layer bridging and separate trust assumptions. [eth-danksharding]
- **Solana:** Maintains a single global state without sharding, relying on high hardware specifications, multi-threading, and pipelining (Sealevel). [solana-arch] (unverified in this book).

## Strengths and weaknesses (feeds the Honest take)

**Strengths:**
- Work is horizontally distributed: shards process chunks in parallel. [near-sharding]
- Stateless validation lowers validator hardware overhead and paves the way for dynamic scaling to dozens or hundreds of shards. [near-stateless]
- Transparent UX: human-readable accounts hide shard assignments completely. [near-sharding]

**Weaknesses:**
- Cross-shard transactions are asynchronous and take multiple blocks to finalize. [near-exec]
- Debugging is harder: RPC transaction outcomes do not explicitly report shard IDs without separate protocol config queries. [spike-3]
- Complex protocol mechanics: re-sharding alters boundary accounts over time. [spike-3]
