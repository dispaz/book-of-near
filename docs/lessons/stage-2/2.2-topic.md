# Topic 2.2: Cross-contract calls, receipts, and gas economics

## In one sentence

On NEAR, contracts communicate asynchronously through independent receipts across blocks, with gas allocated upfront and all of the gas they burn destroyed (burned).

## The problem it solves

On synchronous smart contract platforms like Ethereum (EVM), cross-contract calls execute atomically in a single call stack. This creates severe reentrancy vulnerabilities (such as the DAO hack) and forces all contracts involved in a transaction to reside on the same execution thread. [near-cross-contract]

## How it works on NEAR

**Asynchronous Actor Model.**
- Every smart contract runs in its own execution context, similar to an independent actor. [near-cross-contract]
- Invoking another contract does not pause and return a value immediately. Instead, the runtime emits an **Action Receipt** scheduled for execution in a subsequent block or shard. [near-cross-contract]
- Once the destination contract completes execution, it emits a **Data Receipt** carrying the result back to the original caller's callback method. [near-cross-contract]

**No Automatic Multi-Receipt Rollbacks.**
- Within a single transaction's batch of actions on one account, failures roll back all actions (Topic 1.3). [near-anatomy]
- However, across cross-contract calls (multiple receipts), **there is no global atomic rollback**. If contract A calls contract B, and contract B fails or runs out of gas, contract A's initial state changes remain committed on chain. [near-cross-contract]
- Error handling requires a designated **callback method** (conventionally marked private). The callback inspects `PromiseResult` to verify success or manually rollback state and refund balances. [near-cross-contract]

**Gas Mechanics & Units.**
- **Gas Units:** Gas measures computational effort and WebAssembly instructions. 1 Tgas (TeraGas) = $10^{12}$ gas units. [near-gas]
- **Gas Price:** Testnet gas price is typically 100,000,000 yoctoNEAR per gas (0.0001 NEAR per Tgas). [spike-2] [spike-3]
- **Gas Limit:** A single block/chunk has a gas limit (e.g. 1,000 Tgas), and an individual transaction can attach up to 300 Tgas. [near-gas]
- **Budgeting Gas for Callbacks:** Developers must explicitly allocate gas to the target call and keep sufficient static gas for the callback receipt. If the target call consumes all attached gas, the callback never executes, stranding intermediate state. [near-gas]

**Where burnt gas goes: all of it is burned.**
- Each receipt reports its own `gas_burnt` and `tokens_burnt` (spike 4). [spike-2]
- All the gas a function call burns is burned: no account receives it. The NEAR docs: "On protocol version 86 and earlier, contracts also receive 30% of the gas they burn while executing. From protocol version 87 (nearcore 2.14.0), all of it is burned." [near-gas]
- History: up to protocol version 86, the contract account hosting the code got 30% of the gas its code burnt, and 70% was burned. The docs give the version, not a date.
- Checked live on 13 Nov 2026: mainnet and testnet both run protocol version 88 (`status`), and `EXPERIMENTAL_protocol_config` reports `runtime_config.transaction_costs.burnt_gas_reward: [0, 1]` (a 0% reward) on both. The recorded testnet call of the lesson (block 275719637) also ran under protocol version 88. [near-rpc]

## Words to know

- **Action Receipt:** An instruction dispatched to an account requesting an execution step (e.g., calling a method).
- **Data Receipt:** A cryptographic receipt returning the output data of an execution back to a waiting callback.
- **Callback:** A contract method scheduled to run after a cross-contract call completes, receiving its return value or error.
- **Tgas (TeraGas):** $10^{12}$ gas units, the standard conversational unit of gas on NEAR.
- **Gas burnt:** The gas a receipt actually used. It is paid in NEAR at the gas price and destroyed.

## Common misunderstandings

- **"If a cross-contract call fails, all previous state changes revert automatically."** No. Cross-contract execution is non-atomic across receipts. Each receipt commits independently. Reverting state requires manual rollback logic in the callback. [near-cross-contract]
- **"A contract earns 30% of the gas its code burns."** Not any more. That was the rule up to protocol version 86. From protocol version 87 (nearcore 2.14.0), all of it is burned. [near-gas]
- **"A function call can wait synchronously for another contract's reply."** No. Execution terminates and yields control; results only arrive via an asynchronous callback in a later block. [near-cross-contract]

## Compared with Ethereum

- **Ethereum (EVM):** Calls between contracts are synchronous and atomic. If any sub-call reverts, the entire transaction reverts, unless low-level `call` primitives are used. Reentrancy is a constant security risk. [eth-evm]
- **NEAR:** Calls are asynchronous message receipts (Actor model), eliminating classic EVM reentrancy. [near-cross-contract]

## Strengths and weaknesses (feeds the Honest take)

**Strengths:**
- Sharding compatibility: Asynchronous receipts can cross shard boundaries without locking global state. [near-sharding]
- Protection against reentrancy: Calling another contract relinquishes control until a fresh callback receipt is processed. [near-cross-contract]

**Weaknesses:**
- Complex error recovery: Developers must write defensive callback logic to unwind failed trades or refunds. [near-cross-contract]
- Latency: Multi-hop calls take multiple blocks (~1 second per hop) to reach final settlement. [near-cross-contract]
- Risk of callback starvation: Forgetting to reserve gas for a callback can leave user funds trapped in intermediary contracts. [near-gas]
