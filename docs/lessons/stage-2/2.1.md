# Lesson 2.1: Follow your transaction across shards

Issue: #17. Target time: 5 minutes. Chain access: read-only (testnet RPC through the `Chain` interface) or demo mode (the demo transaction or a recorded one). Showpiece, 3D first, with a flat 2D view of the same state.

Scope (owner, 2 Nov 2026): 0.3 already timed a transfer. This lesson does **not** send or time a new transaction. It opens the learner's own 0.3 transaction (its `txHash` is in the 0.3 evidence) and shows where its time went: which shard, chunk and block handled each receipt. If 0.3 was skipped, it opens a recorded example.

## 1. Learning goals

1. Say what a shard, a chunk and a block are, and how they fit together.
2. Read one transaction as a path: a hop per receipt, each on one shard in one block.
3. Explain why a transaction takes more than one block, and name NEAR's trade-off against Ethereum rollups and one global state.

## 2. Steps

### Step 1: Pick a transaction
- **Caption:** Pick a transaction to follow. Yours from 0.3 is the first choice.
- **Explain:** A **transaction ID** is the hash from 0.3. The app asks an RPC node (through the app's Chain layer) for what happened to it. Nothing new is sent. If you skipped 0.3, the app uses a **recorded example**: a real testnet transaction saved on 1 Nov 2026.
- **Action:** Two choices: "My 0.3 transaction" (disabled with a hint when there is none) and "Recorded example". Choosing loads the trace. Next unlocks when it is loaded.

### Step 2: Shards, chunks and blocks
- **Caption:** NEAR splits its work between shards. Every block holds one chunk per shard.
- **Explain:** A **shard** is a slice of the network's accounts. A **chunk** is the work one shard did in one block. The grid shows time left to right (one column per block) and one row per shard. Testnet has 10 shards; the number changes when the network resplits, so the app reads it live.
- **Action:** None (look). Gate opens at once.

### Step 3: Where it started
- **Caption:** Your transaction started on shard {firstShard}, in block {firstBlock}.
- **Explain:** An account lives on exactly one shard, picked by sorting account names against a list of **boundary accounts**. The transaction runs on the **signer's** shard, in the chunk that shard made in that block. There it is turned into a **receipt**: a message that the receiver's shard will act on.
- **Action:** The first cell of the path is lit with shard id, block height and chunk hash. Gate opens at once.

### Step 4: Follow the receipts
- **Caption:** Follow each receipt: {hops} steps, {touched}, {blocks}.
- **Explain:** A receipt is routed to the receiver's shard and runs there, in a later block. A refund of unused gas is a receipt too, and it goes back to the signer's shard. A transaction that stays on one shard still spends one block per step.
- **Action:** Button **Follow next receipt** moves a marker one step along the path and shows account, shard, block and chunk. Gate opens at the last step.

### Step 5: Where the time went
- **Caption:** Remember {finalSeen}? Here is where it went: {workTime} of block-to-block steps.
- **Explain:** Blocks are about half a second to a second apart. Each step waited for the next block. The rest of what you saw in 0.3 was the hand-over to the RPC node and waiting for **finality**. Times here come from block timestamps.
- **Action:** A timeline of the steps with their offsets from the first block. Gate opens at once.

### Step 6: Quick check
- **Caption:** Three quick questions. Then the honest take.
- **Action:** Check (section 4).

### Step 7: Honest take
- **Caption:** Honest take: what sharding gives NEAR, and what it costs.

## 3. Glossary terms
**Shard**, **chunk**, **boundary account**, **receipt** (already in 0.3 as "network step"), **finality**.

## 4. Check
**Q1. What is a chunk?**
- The work one shard did in one block. **(correct)**
- A piece of your private key. *Wrong: keys are not involved.*
- Another word for a transaction. *Wrong: a chunk holds many transactions and receipts.*

**Q2. Which shard runs your transaction first?**
- The shard of the account that signed it. **(correct)**
- The shard of the receiver. *Wrong: the receiver's shard runs the receipt in a later block.*
- A random shard. *Wrong: the account name decides the shard.*

**Q3. Why can one transaction take several blocks?**
- Each receipt runs in a later block, and a refund receipt follows. **(correct)**
- The network waits for you to approve each step. *Wrong: nothing waits for you.*
- Shards take turns, one per block. *Wrong: every shard makes a chunk in every block.*

## 5. Honest take
**Strengths**
- **Work is split.** Each block carries one chunk per shard, so shards can work side by side. [near-exec] [nomicon]
- **Invisible to users.** You use one account and one address; the app finds the shard. [near-exec]
**Weaknesses**
- **Cross-shard calls take extra blocks.** A receipt that crosses to another shard runs one block later, so a call is not atomic in one step like Ethereum's or Solana's single-state calls (unverified for Solana in this book). [near-exec]
- **Hard to read.** A transaction status carries no shard id; apps must work it out from the shard layout. [spike 3]
- **Ethereum chose rollups.** ethereum.org says shard chains are no longer on its roadmap; it scales by rollups that batch transactions and post results to Ethereum. Rollups add a second layer to trust and bridge; sharding keeps one chain, with extra complexity inside. [eth-danksharding]
- **The layout changes.** Testnet has 10 shards with non-contiguous ids today (1 Nov 2026) and resharding changes it. [spike 3]
