# Lesson 2.1: Follow your transaction across shards

Issue: #17. Target time: 5 minutes. Chain access: read-only (testnet RPC through the `Chain` interface) or demo mode (the demo transaction or a recorded one). Showpiece, 3D first, with a flat 2D view of the same state.

Topic: `2.1-topic.md` (the source of truth for what this lesson teaches).

Scope (owner, 2 Nov 2026): 0.3 already timed a transfer. This lesson does **not** send or time a new transaction. It opens the learner's own 0.3 transaction (its `txHash` is in the 0.3 evidence) and shows where its time went: which shard, chunk, and block handled each receipt. If 0.3 was skipped, it opens a recorded example.

## 1. Learning goals

1. Say what a shard, a chunk, and a block are, and how they fit together.
2. Read one transaction as a path: a hop per receipt, each on one shard in one block.
3. Explain why a cross-shard transaction takes more than one block, and name NEAR's trade-off against Ethereum rollups and Solana's single state.

## 2. Steps

### Step 1: Hook (Pick a transaction)

- **Caption:** Where did your transaction go after you pressed Send? Watch it travel across parallel shards.
- **Explain:** In Lesson 0.3, you sent a transaction and saw "Final" after about 2.5 seconds. The app asks an RPC node for the complete trace of what happened. If you skipped 0.3, the app loads a **recorded example**: a real testnet transaction with multiple hops.
- **Scene:** The learner's account mailbox on the desk. A choice card with two options: "My 0.3 transaction" (disabled with a helpful hint if none exists) and "Recorded example".
- **Action:** Button **Load transaction path**. Gate opens when the trace is loaded.

### Step 2: Shards, chunks, and blocks

- **Caption:** NEAR splits accounts across parallel tracks called shards. Every block holds one chunk per shard.
- **Explain:** A **shard** is a slice of the network's accounts. A **chunk** is the work one shard packaged for one block. On wide screens, the scene lays out a grid: time flows left to right (blocks), and each row is a shard. Testnet has 10 shards; the app reads the layout live from the protocol configuration.
- **Scene:** The grid of shards, each marked with its colored ribbon. Rows represent shards; vertical columns represent blocks. Empty block page slots wait to be filled.
- **Action:** None (visual introduction). Next is open immediately.

### Step 3: Where it started

- **Caption:** Your transaction started on shard {firstShard}, in block #{firstBlock}.
- **Explain:** An account lives on exactly one shard, decided by sorting account names against a list of **boundary accounts**. The transaction runs on the **signer's** shard, in the chunk that shard produced for that block. There, it turns into an **Action Receipt**: a delivery slip destined for the receiver's shard.
- **Scene:** The signer's mailbox lights up in the stage accent color. The first cell of the grid highlights with the chunk hash and block height. A delivery slip rises from the parcel.
- **Action:** Pickable first chunk. Next is open.

### Step 4: Follow the receipts

- **Caption:** Follow each receipt hop: {hops} steps across {shardsTouched} shards and {blocksCount} blocks.
- **Explain:** A receipt travels across the network to the receiver's shard and executes in a later block. A refund of unspent gas is a receipt too, returning to the signer's shard. Each hop between shards takes at least one block boundary.
- **Scene:** The delivery slip hops along an arc from the signer's shard row to the receiver's shard row in the next block column. Successful steps show a green checkmark; gas refunds show a returning slip.
- **Action:** Button **Follow next receipt** advances the traveler marker step-by-step along the path. Gate opens when the final receipt is reached.

### Step 5: Where the time went

- **Caption:** Remember the {finalSeen} seconds? Here is where it went: {workTime} of block-to-block hops, plus finality.
- **Explain:** Blocks occur roughly every second. Each receipt waited for the next block to be produced. The rest of the time was the initial broadcast to the RPC node and waiting for validator consensus (**finality**).
- **Scene:** A timeline bar breaking down the seconds: RPC Broadcast (~250ms), Shard Hops (~1.5s), and Finality (~800ms).
- **Action:** Button **Inspect breakdown**. Next is open.

### Step 6: Quick check (summary page)

- **Caption:** Three quick questions on shards, chunks, and receipts.
- **Action:** Check (section 3).

### Step 7: Honest take

- **Caption:** Honest take: What sharding gives NEAR, and what it costs.
- **Gate:** Gated until the learner traced the path in step 4.

## 3. Check

**Q1. What is a chunk on NEAR?**
- A. The slice of transactions and receipts executed by one specific shard for one block. **(correct)**
- B. A piece of the user's private key. *Wrong: keys are for authentication; chunks are blocks of transactions.*
- C. A synonym for an entire blockchain. *Wrong: a chunk is only one shard's contribution to a block.*

**Q2. Which shard runs your transaction first?**
- A. The shard that holds the signer's account. **(correct)**
- B. The shard that holds the receiver's account. *Wrong: the receiver's shard runs the subsequent receipt in a later block.*
- C. A random shard chosen by lottery. *Wrong: account names deterministically decide shard placement via boundary accounts.*

**Q3. Why does a transaction involving multiple contracts take several blocks?**
- A. Each cross-contract receipt executes in a subsequent block, often across different shards. **(correct)**
- B. Because the user must sign a new password for each step. *Wrong: the user signs once upfront.*
- C. Because shards take turns producing blocks one at a time. *Wrong: all shards produce chunks in parallel every block.*

## 4. Honest take

**Strengths:**
- **Parallel throughput:** Work is partitioned across shards; adding shards increases total network capacity without slowing down nodes. [near-sharding]
- **Invisible to users:** You use simple named accounts; the network automatically routes transactions and receipts to the correct shards behind the scenes. [near-sharding]
- **Stateless validation:** Validators verify chunks without storing entire shard databases on disk, keeping validator hardware requirements accessible. [near-stateless]

**Weaknesses:**
- **Multi-block receipt latency:** Cross-shard calls are not atomic within a single block like Ethereum or Solana; each hop adds at least one block of delay (~1 second). [near-exec]
- **Hard to trace via simple RPC:** Standard transaction status queries omit shard IDs; applications must look up protocol boundary configs to identify which shard handled a chunk. [spike-3]
- **Ethereum chose rollups:** Ethereum abandoned execution sharding in favor of Layer 2 rollups (Danksharding for blob data), avoiding cross-shard receipt complexities while introducing bridge and L2 fragmentation trade-offs. [eth-danksharding]

Compared with: **Ethereum** (L2 rollups instead of sharding) and **Solana** (single global state, no sharding).
