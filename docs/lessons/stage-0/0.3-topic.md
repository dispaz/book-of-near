# Topic 0.3: Transaction Lifecycle: Build, Sign, Broadcast, Included, and Final

The source of truth for lesson 0.3. The lesson script (`0.3.md`) and the code may only teach what this
file says. Facts carry a source tag; anything else is marked (unverified).

## In one sentence

Sending a blockchain transaction follows a strict 5-stage pipeline—Build, Sign, Broadcast, Included, and Final—where network nodes validate signatures, package transactions into blocks, and reach irrevocable consensus in ~2 to 3 seconds.

## The problem it solves

When a user taps "Send" in a banking app, the bank updates a private server database in milliseconds. On a decentralized network, a transaction must be cryptographically signed, broadcast across an untrusted peer-to-peer network, validated against account balance and nonces, ordered into blocks, and confirmed by validator consensus without conflicting with concurrent transactions. [near-lifecycle]

## How it works

**The 5-Stage Transaction Pipeline.** [near-lifecycle]

| Stage | What Happens | Where it Happens |
| :--- | :--- | :--- |
| **1. Build** | The transaction payload is constructed with signer, receiver, actions, a recent block hash, and a rising key nonce. | Locally on user's device. |
| **2. Sign** | The user's private key cryptographically signs the binary Borsh-serialized transaction hash. | Locally on user's device (keys never leave). |
| **3. Broadcast** | The signed transaction is sent via HTTP JSON-RPC to a gateway RPC node. | Sent to RPC node network. |
| **4. Included** | The transaction is validated by validators and packed into a chunk and block on the blockchain. | Signer's shard on chain. |
| **5. Final** | Validators finalize the block containing the execution outcome via Doomslug consensus (~1-2 seconds). | Consensus network. |

**Key Fields in a Transaction.** [near-anatomy]
- **Signer ID:** The account authorizing and paying for the transaction.
- **Receiver ID:** The account receiving the action (e.g. the recipient of funds or the contract called).
- **Nonce:** A sequential counter incremented for each transaction signed by an access key, preventing replay attacks.
- **Recent Block Hash:** Proves the transaction is fresh; expires if the block referenced is older than the validity window.
- **Gas & Attached Deposit:** Attached deposit transfers balance; gas covers computational instructions.

**Block Explorers (NearBlocks).**
- A **block explorer** (such as NearBlocks) is a public web search engine for the blockchain.
- It displays transaction hashes, block numbers, gas used, tokens burnt, and execution receipt outcomes directly from RPC indexing nodes. [near-rpc]

## Words to know

- **RPC Node (Remote Procedure Call):** The gateway server through which wallets and apps communicate with the blockchain.
- **Nonce:** A unique incrementing number tied to an access key ensuring each transaction can only execute once.
- **Included:** When a transaction has been successfully ordered and sealed into a new block chunk.
- **Finality:** The point in time after which a transaction is cryptographically irreversible and cannot be rolled back.
- **Block Explorer:** A public web interface for inspecting transactions, blocks, and account balances.

## Common misunderstandings

- **"Pressing Send means the transaction is complete."** No. Send only submits the transaction to an RPC node. It must still be included in a block and reach finality before the funds are guaranteed. [near-lifecycle]
- **"The RPC node can forge a signature."** No. Transactions are signed locally on the client's device before broadcast. RPC nodes can only forward or reject malformed transactions; they cannot alter signed contents. [near-lifecycle]

## Compared with Ethereum & Bitcoin

- **Finality Speed:**
  - Bitcoin: ~60 minutes (6 confirmations).
  - Ethereum: ~12–15 minutes (2 epochs under Gasper).
  - NEAR: ~1.5–3 seconds (Doomslug single-round finality under normal conditions). [near-lifecycle] [spike-3]
- **Explorer Transparency:** Both use public explorers (Etherscan on Ethereum, NearBlocks on NEAR) displaying full transaction receipts and execution logs.

## Strengths and weaknesses (feeds the Honest take)

**Strengths:**
- Rapid finality: User transactions reach true irreversible finality in ~2.5 seconds. [spike-3]
- Deterministic lifecycle: Real-time phase status notifications via JSON-RPC (`INCLUDED`, `FINAL`). [near-rpc]

**Weaknesses:**
- Slower than Web2 databases: 2.5 seconds is fast for crypto, but slower than centralized SQL writes (10ms). [near-lifecycle]
- RPC dependency: If the user's selected RPC node is slow or congested, broadcast can time out even if the blockchain itself is healthy. [near-rpc]
