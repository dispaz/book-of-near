# Lesson 0.1: How a blockchain and a transaction work

Issue: #8. Target time: 4 minutes. Chain access: none (pure in-browser toy, same in demo and testnet mode).

## 1. Learning goals

1. Explain a blockchain as a shared list of transactions, grouped into blocks that link by hash.
2. Show why editing an old block is easy to detect: it breaks every later link.
3. Say what blockchains are slow or bad at, compared with a normal database.

## 2. Steps

Each step: **caption** (caption bar, ≤ 160 chars), **explain** (≤ 60 words, the "more" panel), **action** (what the learner does, what the scene shows, what unlocks Next).

### Step 1: A shared notebook

- **Caption:** Ana, Ben and Cy keep one notebook of who owns how many coins. Everyone holds a copy.
- **Explain:** A **ledger** is a list of who owns what. Banks keep their own ledger and you trust them. Here the three friends each keep an identical copy. Nobody is in charge, so they must agree on every new line.
- **Action:** Scene shows three account blocks (Ana 10, Ben 5, Cy 0) and three identical notebook copies. Learner clicks any notebook to see the same balances. Next unlocks after one click.

### Step 2: Move some coins

- **Caption:** Send 3 coins from Ana to Ben. A request to change the ledger is called a transaction.
- **Explain:** A **transaction** is a request to change the ledger, such as "Ana pays Ben 3". It is checked first: Ana must own at least 3 coins. If the check fails, the transaction is rejected and nothing changes.
- **Action:** Pre-filled form "Ana → Ben, 3 coins". Learner presses **Send**. A coin travels from Ana to Ben; balances become Ana 7, Ben 8. If the learner edits the amount above Ana's balance, the scene shows "Rejected: Ana only has 10". Next unlocks after one accepted transaction.

### Step 3: Transactions go into blocks

- **Caption:** Transactions are packed into a block. A new block is added to the end of the chain.
- **Explain:** A **block** is a page of the notebook: a batch of transactions written down together. Blocks are only ever added to the end. Bitcoin aims for one block about every 10 minutes. NEAR makes a block about every second or less.
- **Action:** The Ana → Ben transaction drops into a new block #1 that attaches to block #0 (genesis, the starting balances). Learner clicks block #1 to open it. Next unlocks after opening it.

### Step 4: A fingerprint for each block

- **Caption:** Each block gets a hash: a short fingerprint of everything inside it. Change one letter and the fingerprint changes.
- **Explain:** A **hash** is a short code computed from data. The same data always gives the same hash. Any small change gives a completely different hash. You cannot work backwards from the hash to the data. This toy uses SHA-256 and shows the first 8 characters.
- **Action:** Block #1 panel shows its contents and hash `93fa7ab6`. Learner types into a sandbox field ("Ana->Ben 3" → "Ana->Ben 4") and sees the hash change. Next unlocks after the hash has changed once.

### Step 5: Blocks link by hash

- **Caption:** Each block also stores the hash of the block before it. That is the chain in "blockchain".
- **Explain:** Every block records the previous block's hash. So block #2 depends on block #1, which depends on block #0. Bitcoin works this way: each block stores the hash of the previous block's header.
- **Action:** Learner sends two more transactions (Ben → Cy 2, then Cy → Ana 1). Blocks #2 and #3 appear. Each shows "prev: ..." pointing with an ink arrow to the previous block's hash. Next unlocks when block #3 exists.

### Step 6: Try to rewrite history

- **Caption:** Pretend you are Ben. Change block #1 so Ana sent you 9 coins, not 3. Watch what happens.
- **Explain:** Block #1's hash changes. Block #2 still stores the old hash, so the link breaks. Fixing block #2 changes its hash, which breaks block #3, and so on. To hide the edit you must redo every later block.
- **Action:** Learner clicks the amount in block #1 and changes 3 to 9. Block #1's hash becomes `6c3c0e30`. Every link after it turns red and cracks (block #2 expects `93fa7ab6`). Learner may press **Repair next block**: block #2 is re-hashed, its link to #3 now breaks. Next unlocks once every later link is red.

### Step 7: The others still hold the true copy

- **Caption:** Ana and Cy compare their copies with Ben's. The hashes do not match, so they reject Ben's version.
- **Explain:** Everyone can check the chain by recomputing hashes. A changed copy stands out at once. Real networks add rules for who may add the next block and what makes a block valid. Those rules are called **consensus**. Stage 2 shows NEAR's version.
- **Action:** Ben's notebook glows red next to two matching notebooks. Learner presses **Compare copies**. The tampered copy is crossed out and the honest chain is restored. Next unlocks after the comparison.

### Step 8: Quick check

- **Caption:** Three quick questions. Then the honest take.
- **Explain:** (none)
- **Action:** Check (section 4). Then the Honest take card. Completing both emits the completion record.

## 3. Glossary terms introduced

- **Ledger:** a list of who owns what.
- **Transaction:** a request to change the ledger, checked before it is accepted.
- **Block:** a batch of transactions added to the end of the chain together.
- **Genesis block:** the first block, holding the starting balances.
- **Hash:** a short fingerprint of some data. Same data, same hash. Small change, very different hash.
- **Blockchain:** a list of blocks where each block stores the hash of the block before it.
- **Consensus:** the rules a network uses to agree on the next block (named only; explained in Stage 2).

## 4. Check

**Q1. Why does changing an old block break the chain?**
- A. The block's hash changes, and the next block still stores the old hash. **(correct)**
- B. The network deletes any block older than one hour. *Wrong: blocks are never deleted; the problem is the hash link.*
- C. Old blocks are locked with a password. *Wrong: there is no password; anyone can read and recompute the hashes.*
- D. Coins in old blocks expire. *Wrong: nothing expires; the mismatch comes from the hash.*

**Q2. Ana has 7 coins. She tries to send Ben 9. What happens?**
- A. The transaction is rejected and no balances change. **(correct)**
- B. Ana's balance goes to −2. *Wrong: the ledger checks a transaction before accepting it.*
- C. Ben gets 7 coins and the rest is skipped. *Wrong: a transaction is accepted whole or not at all.*

**Q3. What does a block's hash do?**
- A. It acts as a fingerprint: any change to the block gives a different hash. **(correct)**
- B. It encrypts the block so nobody can read it. *Wrong: a hash does not hide the data; blocks are public.*
- C. It records the time the block was made. *Wrong: that would be a timestamp, not a hash.*
- D. It shows how many coins are in the block. *Wrong: the hash is a fingerprint, not a balance.*

## 5. Honest take

**Strengths**
- **Tamper-evident history.** Any change to an old block breaks every later link, so everyone can spot it by recomputing hashes. Bitcoin's own guide says a transaction "cannot be modified without modifying the block that records it and all following blocks". [bitcoin-chain]
- **No single owner.** Nobody has to trust one bank's private copy of the ledger. Everyone can check the same public history.
- **NEAR is fast for a blockchain.** NEAR docs give a block time of about 600 ms and finality around 1.2 s, against about 12 s per Ethereum slot and a 10-minute target for Bitcoin. [near-finality] [eth-pos] [bitcoin-chain]

**Weaknesses**
- **Slower and costlier than a normal database.** Many computers must store and agree on every change. A single company database is far quicker and cheaper when you can trust its owner. (This is true of all blockchains, NEAR included.)
- **Public by default.** On Bitcoin, Ethereum and NEAR, transactions and balances are visible to anyone with an explorer. Privacy needs extra tools.
- **Mistakes are hard to undo.** Once a transaction is final there is no bank to call. A typo in the amount or receiver stays in the history.

## 6. Demo-mode data

Toy ledger (no chain call; identical in both modes).

- Accounts and starting balances (genesis, block #0): Ana 10, Ben 5, Cy 0. Unit label: "coins" (not NEAR, to keep the toy separate from real tokens).
- Default transactions, one per block: #1 `Ana->Ben 3`, #2 `Ben->Cy 2`, #3 `Cy->Ana 1`. Balances after #3: Ana 8, Ben 6, Cy 1.
- Hash rule: `sha256(height + "|" + prevHashHex + "|" + txText)` as lowercase hex; show the first 8 chars. Genesis `prevHashHex` is 64 zeros; genesis `txText` is `genesis: Ana=10, Ben=5, Cy=0`.
- Expected hashes (precomputed with that rule; use as test fixtures):

| Block | txText | Hash (first 8) |
| --- | --- | --- |
| #0 | `genesis: Ana=10, Ben=5, Cy=0` | `48d4cf70` |
| #1 | `Ana->Ben 3` | `93fa7ab6` |
| #2 | `Ben->Cy 2` | `46c2f4b1` |
| #3 | `Cy->Ana 1` | `3e875716` |

- Tamper fixture: change #1 to `Ana->Ben 9`. Recomputed live from the new hashes: #1 `6c3c0e30`, #2 `97b846de`, #3 `c1495fa1`. All three differ from the recorded hashes, so every link after #0 shows red.
- Rejection fixture: any amount above the sender's balance shows "Rejected: <name> only has <n>".
- Timing: one block per Send, 600 ms block animation (mirrors NEAR's documented ~600 ms block time; not a protocol claim).
