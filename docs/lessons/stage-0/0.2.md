# Lesson 0.2: Make a wallet

Issue: #9 (tier A showpiece, never cut). Target time: 5 minutes. Chain access: none. Everything runs in the browser and nothing is sent anywhere, in both demo and testnet mode.

## 1. Learning goals

1. Explain a wallet as a key pair: the private key signs, the public key lets anyone verify.
2. Show how an address comes from a public key on NEAR (implicit account) and on Ethereum, and what a NEAR named account adds.
3. Treat a seed phrase as the master key: never type a real one into any website, this one included.

## 2. Steps

### Step 1: Warning first (shown before any key exists)

- **Caption:** Never type a real seed phrase into any website, including this one. We will only make throwaway keys.
- **Explain:** A **seed phrase** is a list of words that can rebuild your keys. Anyone who sees it can take everything the keys control. Real wallets never ask you to paste it into a page. If a site asks, it is a scam.
- **Action:** Full-width warning card with ink border in the stage accent colour. The **Generate** button stays disabled until the learner ticks "I understand: these keys are for practice only". Next unlocks after the tick. (Acceptance criterion: warning visible before any key is generated.)

### Step 2: Generate a key pair

- **Caption:** Press Generate. Your browser makes a private key and a public key. Nothing leaves this page.
- **Explain:** A **key pair** is two linked numbers. The **private key** is secret and is used to sign. The **public key** is shared and lets others check your signatures. You cannot work out the private key from the public one. NEAR mostly uses the **ed25519** key type.
- **Action:** Learner presses **Generate**. The scene draws a key (private, hidden behind a "show" toggle) and a padlock (public). Public key shown as `ed25519:<base58>`. A small "offline" badge confirms no network request. Next unlocks after generation.

### Step 3: The seed phrase behind the keys

- **Caption:** These 12 words can rebuild the same keys on any wallet. Lose them and you lose the keys. Share them and you lose everything.
- **Explain:** The words follow a standard called **BIP-39**: 12 words from a fixed list of 2,048. A second standard, **SLIP-10**, turns the words into a key along a path. NEAR uses the path `m/44'/397'/0'`; 397 is NEAR's registered number.
- **Action:** The 12 words appear on a "paper" card stamped PRACTICE ONLY. Learner presses **Rebuild from words**; the same public key reappears. Next unlocks after the rebuild matches.

### Step 4: From public key to NEAR address

- **Caption:** On NEAR, your public key written in hex is already an account address. This is called an implicit account.
- **Explain:** An **address** is where others send you tokens. A NEAR **implicit account** is the 32-byte ed25519 public key written as 64 hex characters (0–9, a–f). It exists on chain only after someone sends it some NEAR, even 0 NEAR.
- **Action:** Animated conversion: `ed25519:<base58>` → decode → 32 bytes → 64 hex chars. Learner clicks **Copy address** (or taps the address). Next unlocks after the conversion animation finishes or is skipped.

### Step 5: Compare with Ethereum and with NEAR names

- **Caption:** Ethereum hashes the public key and keeps the last 20 bytes. NEAR also lets you use a readable name like ana.testnet.
- **Explain:** On Ethereum, an address is the last 20 bytes of the Keccak-256 hash of the public key, shown as `0x` plus 40 hex characters. On NEAR, a **named account** like `ana.testnet` is a readable name. It can hold several keys and change them later. Stage 1 creates one.
- **Action:** Three cards side by side: Ethereum `0x…` (40 hex), NEAR implicit (64 hex, from step 4), NEAR named (`ana.testnet`). Learner presses "Show the … rule" on each card to see its rule. Next unlocks after all three rules are shown.

### Step 6: Sign a message

- **Caption:** Type a short message and sign it with your private key. The result is a signature.
- **Explain:** A **signature** is a code made from the message and the private key. Only the private key can make it. With ed25519, the same key and message always give the same signature. Signing a transaction works the same way, as you will see in 0.3.
- **Action:** Text field pre-filled with `Hello from Book of NEAR`. Learner presses **Sign**. The key stamps the message; a 64-byte signature appears (base58). Next unlocks after signing.

### Step 7: Verify, then tamper

- **Caption:** Anyone can check the signature with your public key. Now change one letter and check again.
- **Explain:** **Verifying** uses the message, the signature and the public key. If anything changed, the check fails. This is how a blockchain knows a transaction really came from the account owner and was not altered on the way.
- **Action:** Learner presses **Verify**: green tick. Then edits one letter (e.g. `Hello` → `Hellp`) and presses **Verify** again: red cross, "Signature does not match this message". Next unlocks only after both a pass and a fail.

### Step 8: Who holds the key holds the account

- **Caption:** No bank can reset this key. Holding your own keys is called self-custody. It is freedom and responsibility.
- **Explain:** **Self-custody** means only you hold the private key. Nobody can freeze it, and nobody can recover it for you. Wallet apps store keys and help you sign, but the rule stays the same. The NEAR docs say: "Anyone with access to them can control your account."
- **Action:** Short summary card. Learner presses **Throw the keys away**: keys and words fade out and are cleared from memory. Next unlocks after the clear.

### Step 9: Quick check

- **Caption:** Three quick questions. Then the honest take.
- **Explain:** (none)
- **Action:** Check (section 4), then Honest take. Completing both emits the completion record. The record must not contain any key or seed word.

## 3. Glossary terms introduced

- **Wallet:** an app that stores your keys and signs for you.
- **Key pair / private key / public key:** a secret signing key and the matching shareable key.
- **ed25519:** the main key type NEAR uses; public keys are 32 bytes.
- **Seed phrase:** words that can rebuild your keys (standard: BIP-39).
- **Derivation path:** the route from a seed to one key. NEAR's is `m/44'/397'/0'` (standard: SLIP-10).
- **Address:** what others use to send you tokens.
- **Implicit account:** a NEAR account whose name is the public key in hex (64 characters).
- **Named account:** a readable NEAR account name such as `ana.testnet`.
- **Signature / verify:** proof made with the private key; checked with the public key.
- **Self-custody:** you alone hold your keys.

## 4. Check

**Q1. A website asks you to paste your seed phrase to "verify your wallet". What should you do?**
- A. Close the page. Real wallets never need your seed phrase on a website. **(correct)**
- B. Paste it; the site only reads it. *Wrong: whoever sees the phrase can rebuild your keys and take your funds.* <!-- secret-scan:allow public demo key from docs.near.org -->
- C. Paste only the first six words. *Wrong: that leaks half your secret and still helps an attacker.*

**Q2. You change one letter of a signed message. What happens when someone verifies it?**
- A. Verification fails, because the signature no longer matches the message. **(correct)**
- B. It still passes, because the public key is the same. *Wrong: the check covers the message too, not only the key.*
- C. The signature updates itself. *Wrong: only the private key can make a new signature.*
- D. The private key is revealed. *Wrong: verifying never exposes the private key.*

**Q3. What is a NEAR implicit account address?**
- A. The 32-byte ed25519 public key written as 64 hex characters. **(correct)**
- B. The last 20 bytes of the Keccak-256 hash of the public key. *Wrong: that is the Ethereum rule.*
- C. A readable name like `ana.testnet`. *Wrong: that is a named account.*
- D. The seed phrase joined with dashes. *Wrong: the seed phrase is secret and is never an address.*

## 5. Honest take

**Strengths**
- **Readable names and key rotation.** NEAR named accounts like `ana.near` are "easy to remember and share", and one account can hold several keys. The docs note "you can easily swap keys if one gets compromised". On Ethereum a normal address is derived from one key, so a leaked key means moving to a new address. [near-account-id] [near-model] [eth-accounts]
- **Address without a transaction.** An implicit account address can be made fully offline from a key pair, the same as an Ethereum address. [near-account-id]
- **Standard seed phrases.** NEAR uses BIP-39 words and a registered SLIP-44 coin number (397), so the same words rebuild the same key in any compliant NEAR wallet. [bip39] [slip44] [near-implicit-tutorial]

**Weaknesses**
- **Implicit addresses are long and unreadable.** 64 hex characters are easy to mistype, and an implicit account must receive NEAR before it can sign anything. [near-account-id]
- **Two account styles to learn.** Beginners meet hex accounts, named accounts and Ethereum-style `0x` accounts on one chain. [near-model]
- **Seed phrase is a single point of failure.** Lose it and the keys are gone; leak it and they are stolen. This is true on Bitcoin and Ethereum as well. One NEAR seed phrase entered into an Ethereum wallet gives a different address, because the key type (ed25519 vs secp256k1) and path (397 vs 60) differ. [slip44] [eth-accounts]

Live mode generates fresh random keys with the browser's crypto API. Demo mode and e2e tests use one fixed example that is **already public in the NEAR docs**. Say so in the UI: "This example is printed in NEAR's docs, so anyone can use it. Never put funds on it." This doubles as a lesson about public seed phrases. - Seed phrase: `kit creek invite deputy fetch resource marble sweet camp thumb mushroom swift` <!-- secret-scan:allow public demo key from docs.near.org -->
- Derivation path: `m/44'/397'/0'`
- Public key: `ed25519:Ex4stLtTe43ynFmxGweGzMWLvRmRSUP6EjU6nvAdY2vg`
- Secret key (64 bytes, seed + public key, base58): `ed25519:5uJtH8hdYKPEhLVTn9EoxaneLpKh11qLEWDVvG6tKTeMUzsmf7isHYxXixhNcupRhUNQ2fHFgtKXy94YUXHfbxiG` <!-- secret-scan:allow public demo key from docs.near.org -->
- Implicit account: `cf4342372b583606057805490c97d4778bc4ac444a76f32154634558ab57c3c5`
- Message: `Hello from Book of NEAR`; tampered: `Hellp from Book of NEAR`.
- Signature: compute at runtime and snapshot in the test. Ed25519 signatures are deterministic (RFC 8032), so the value is stable across runs.
- Ethereum card: show the rule and a format sample `0x` + 40 hex. Do not derive an Ethereum address from the NEAR key in this lesson; it would imply the same key works on both chains. Stage 4 handles cross-chain addresses. Built: the sample is derived live from a **separate** throwaway secp256k1 key (Keccak-256, last 20 bytes, EIP-55 checksum), and the card says so.
- Named card: `ana.testnet` (illustrative; do not link it, it may belong to someone).

Derivation recipe (for the implementer):
1. `seed = PBKDF2-HMAC-SHA512(password = words (NFKD), salt = "mnemonic", 2048 rounds)` (BIP-39).
2. SLIP-10 ed25519 master: `HMAC-SHA512(key = "ed25519 seed", seed)`; then hardened children 44', 397', 0'. Ed25519 under SLIP-10 supports hardened derivation only.
3. First 32 bytes of the final node = ed25519 private seed; public key from it; implicit account = hex(public key).
