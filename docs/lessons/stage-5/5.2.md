## 1. Learning goals

1. Explain why a bot whose key sits in a `.env` file is not autonomous.
2. Describe a Shade Agent: an agent that makes its key in a TEE, and an agent contract that only lets
   attested, approved code ask for chain signatures.
3. See why the developer cannot sign for the agent, and who still holds power (the contract owner).

## 2. Steps

### Step 1: A bot whose key sits in a file
- **Caption:** Most bots sign with a key that sits in a file.
- **Explain:** A typical bot runs on an ordinary server. The private key that signs for its account sits in a file, often called `.env`. Whoever can read that file can sign anything as the bot: the developer, an attacker or the cloud host. Open the file and see.
- **Action:** "Open the .env file" (gated). Shows `BOT_PRIVATE_KEY=ed25519:…` (an illustration, not a real key) and "Anyone who reads this line can move the bot's funds."

### Step 2: The agent makes its own key, inside the enclave
- **Caption:** A Shade Agent makes its key inside a TEE.
- **Explain:** A Shade Agent has two parts. The agent is a program that runs in a TEE (a sealed area of a chip, lesson 5.1). The agent contract is a NEAR smart contract. When the agent starts, it makes a fresh key pair inside the enclave. Its NEAR account is an implicit account: a 64-character hex name made from the public key. The private key is never saved, so it changes every time the agent restarts. Start the agent.
- **Action:** "Start the agent" (gated). Shows the agent's implicit account (real, made just now in the browser) and "Private key: stays in the enclave (never shown, never saved)".

### Step 3: The agent proves its code to the agent contract
- **Caption:** The agent registers: the contract checks its attestation.
- **Explain:** The agent calls `register_agent` on the agent contract and hands over its attestation quote. The contract checks four things: the quote is genuine; its measurements (hashes of the code, lesson 5.1) are on the approved list; its PPID (an id of the physical chip) is approved; and the quote's report data holds the agent's own account name, so nobody can reuse someone else's quote.
- **Action:** "Register the agent" (gated). Four checks pass. Shows the measurements: MRTD, RTMR0–2 and the app compose hash, labelled "example values: the real measurements from the NEAR AI Cloud quote recorded on 13 Nov 2026 (lesson 5.1)", the line "This model skips one more measurement: a hash of the service that gives the enclave its keys." (the key provider digest; the topic lists six measurements, the model checks five), and "a model of the reference agent contract".

### Step 4: The developer tries to sign
- **Caption:** Can the developer who wrote the agent take its funds?
- **Explain:** The developer never saw the agent's key. First they call `request_signature` on the agent contract from their own account. Then they run a changed copy of the agent in a TEE and try to register it. Try both.
- **Action:** "Sign as the developer": refused, `Agent not registered`. "Register a changed copy": refused, `Attestation verification failed: …`, because the changed code has a different app compose hash, which is not approved. Gated until both are refused.

### Step 5: The agent signs for Ethereum
- **Caption:** The agent asks its contract for an Ethereum signature.
- **Explain:** The agent calls `request_signature` with the path `ethereum-1` and the hash of an Ethereum transaction. The agent contract checks that the agent is still valid, then calls `sign` on the signer contract (`v1.signer-prod.testnet` on testnet). The contract is the caller, so the Ethereum address belongs to the agent contract and the path, not to the agent's key. The funds stay put when an agent restarts or is replaced, and several agents can share them.
- **Action:** "Run the agent" (gated). Shows the call path agent → `request_signature` on `agent.example.testnet` → `sign` on the signer, the arguments (path, payload, 1 yoctoNEAR), and the contract's Ethereum address (derived in the browser from the signer's root key: DemoChain's demo signer in demo mode, labelled; `v1.signer-prod.testnet` in testnet mode).
- **Evidence:** `{ agentContract, agentAccount, derivedAddress, developerRefused: "Agent not registered", copyRefused: "true", contractModel: "reference agent contract (in browser)" }`.

## 3. Check

**Q1. Why is a bot with its key in a `.env` file not autonomous?**
- A. Whoever can read the file (the developer, an attacker, the host) can sign anything as the bot. **(correct)**
- B. Because `.env` files cannot hold keys. *Wrong: they often do, which is the problem.*
- C. Because bots cannot sign transactions. *Wrong: the bot signs with that key.*

**Q2. Whose account does a Shade Agent's Ethereum address belong to?**
- A. The agent contract's: it is derived from the contract's account and a path. **(correct)**
- B. The agent's own key: it changes every restart. *Wrong: the agent's key is ephemeral, so assets are tied to the contract.*
- C. The developer's: they deployed it. *Wrong: the signer derives from whoever calls `sign`, the agent contract.*

**Q3. The developer calls `request_signature` from their own account. What happens?**
- A. The agent contract refuses: "Agent not registered". **(correct)**
- B. It works, because they wrote the code. *Wrong: only registered agents with approved measurements may call it.*
- C. The signing network asks the developer for a password. *Wrong: the agent contract refuses before the signing network is asked.*

## 4. Honest take

**Strengths:**
- No developer holds the agent's key: it is made inside the TEE and never saved. [sa-terms]
- Only attested, approved code can ask for signatures; anyone else gets "Agent not registered". [sa-contract]
- One agent contract can sign for most chains through chain signatures. [sa-overview]
- The assets sit with the contract, so agents can restart, be replaced or run as several copies. [sa-terms]

**Weaknesses:**
- The contract owner approves new code (measurements). The framework says the owner should be a multisig and the contract account's access keys must be removed, or that owner can still move the funds. [sa-security]
- TEEs are not absolute: TEE.fail showed a host with physical access can pull secrets out of Intel TDX, so the contract's guardrails matter. [sa-security]
- The host can pause the agent at any time: you need several agents, and protection against doing an action twice. [sa-security]
- NEAR's docs mark the Shade Agent Framework deprecated: not maintained since 19 April 2026, not for new projects. [near-docs-shade]
- This page runs a model of the contract in your browser; no agent ran here.

Compared with: **a bot with a key in `.env`** (whoever reads the file can sign) and **a human multisig** (people approve every action; slower, but no TEE to trust).
