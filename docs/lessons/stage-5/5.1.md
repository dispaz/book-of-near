# Lesson 5.1: Ask a private AI and verify it

Issue: #38. Target time: 5 minutes. Chain access: read-only attestation verification in the browser or demo mode. Views: 2D and 3D, one shared state.

Facts come from `docs/lessons/stage-5/5.1-topic.md`. Anything else is marked (unverified).

## 1. Learning goals

1. Explain how a Trusted Execution Environment (TEE) isolates AI prompts from cloud operators.
2. Fetch a hardware remote attestation quote and verify its silicon signature.
3. Understand why confidential computing is essential for sovereign User-Owned AI.

## 2. Steps

### Step 1: The AI privacy problem
- **Caption:** Who can read your prompts? When using ChatGPT or Claude, the cloud host sees everything in plaintext.
- **Explain:** Standard web servers decrypt your data in RAM. Cloud operators, hosting providers, and software engineers can log your questions, private data, and medical queries. NEAR AI changes this using hardware enclaves.
- **Scene:** A user terminal sending a prompt to a standard open server vs. a locked silicon enclave box. Next is open.

### Step 2: The hardware enclave (TEE)
- **Caption:** A Trusted Execution Environment (TEE) seals memory in hardware with silicon-level encryption.
- **Explain:** In an Intel TDX or NVIDIA confidential GPU enclave, memory keys are generated inside the chip. Neither the operating system administrator nor the cloud provider can read the memory. It is called the **triple lockout**.
- **Scene:** Visualizing the CPU/GPU with an impenetrable encrypted perimeter; root access attempts bounce off. Next is open.

### Step 3: Send a prompt to the AI tutor
- **Caption:** Ask the Book of NEAR tutor a question. The model runs completely inside the enclave.
- **Explain:** Type a question (e.g. "Why does NEAR use sharding?"). The prompt is transmitted over an encrypted channel straight into the enclave.
- **Action:** Text box with sample prompts. Button "Send prompt". The model streams back the response in real time.
- **Demo data:** Cached educational response returned immediately in demo mode.

### Step 4: Fetch the remote attestation quote
- **Caption:** How do you know it ran in a real enclave? The processor signs a hardware proof.
- **Explain:** Anyone can claim they run in a TEE. To prove it, the chip generates an **attestation quote**: a binary report containing a cryptographic hash of the enclave code, signed by a secret key burned into the silicon at the factory.
- **Action:** Button "Fetch attestation quote". Inspect the measurement hash and silicon certificate chain.

### Step 5: Verify the signature
- **Caption:** Verify the manufacturer root certificate. The math proves nobody tampered with the AI.
- **Explain:** The client checks the signature against the chipmaker's public key (Intel/NVIDIA). If a single line of model code had been altered or monitored, verification would fail.
- **Action:** Button "Cryptographically verify". The badge turns green: "Verified Authentic Enclave".
- **Evidence:** `{ attestationHash, verified: true }`.

### Step 6: Quick check (summary page)
- **Caption:** Three questions on TEEs, attestation, and private inference.
- **Action:** Check (section 3).

### Step 7: Honest take
- **Caption:** Honest take: Hardware enclaves vs zero-knowledge ML and centralized AI.
- **Gate:** Gated until attestation verification passes.

## 3. Check

**Q1. What makes a TEE different from standard cloud server hosting?**
- A. The processor encrypts memory in hardware so even root admins cannot read it. **(correct)**
- B. It requires users to pay with Bitcoin instead of credit cards. *Wrong: payment method is unrelated to hardware security.*
- C. It deletes your data only after 30 days. *Wrong: enclaves protect data while actively running in RAM.*

**Q2. What is a remote attestation quote?**
- A. A cryptographic proof signed by physical silicon certifying the enclave's code integrity. **(correct)**
- B. A price quotation from an AI sales representative. *Wrong: an attestation is a cryptographic hardware certificate.*
- C. A legal contract signed between NEAR and Apple. *Wrong: it is an automated hardware signature.*

**Q3. If the host administrator tries to dump the server's RAM while the AI runs, what do they see?**
- A. Indecipherable encrypted noise. **(correct)**
- B. Plaintext user prompts and passwords. *Wrong: memory encryption prevents plaintext inspection.*
- C. The user's private seed phrase. *Wrong: user seed phrases never touch the AI server.*

## 4. Honest take

**Strengths:**
- **True prompt privacy:** Hardware-enforced encryption stops server operators from inspecting user conversations. [near-ai-vision]
- **High throughput:** Runs full LLMs on confidential GPUs (NVIDIA H100) at native inference speeds. [nvidia-cc]
- **Cryptographic verifiability:** Anyone can independently verify that outputs came from the exact specified model weights. [near-ai-vision]

**Weaknesses:**
- **Hardware vendor trust:** You must trust that Intel, AMD, and NVIDIA did not introduce backdoors or secret keys during chip manufacturing. [tee-overview]
- **Physical side-channel risks:** Sophisticated timing or power-analysis attacks occasionally require silicon firmware updates. [tee-overview]

Compared with: **Centralized Web2 AI** (OpenAI/Anthropic) and **Zero-Knowledge Machine Learning (ZKML)** (ZKML provides mathematical proofs without hardware trust, but is thousands of times too slow for large LLMs).
