# Topic 5.2: Shade Agents (an agent in a TEE that signs through an agent contract)

The source of truth for lesson 5.2. The lesson script (`5.2.md`) and the code may only teach what this
file says. Facts carry a source tag; anything else is marked (unverified).

Rewritten on 13 Nov 2026 against the Shade Agent Framework's own docs and reference contract
([sa-docs], [sa-contract]). The earlier draft said the agent's address is derived from the enclave's code
hash and that the MPC contract refuses the developer with "Caller is not the verified enclave". Both were
wrong: the address belongs to the **agent contract**, and the refusal comes from the agent contract
("Agent not registered").

## In one sentence

A Shade Agent is a program that runs in a TEE and makes its own key there; a NEAR smart contract (the
agent contract) only lets agents whose attestation shows approved code ask for chain signatures, and the
assets belong to that contract, so the developer never holds a key that can move them. [sa-docs]

## The problem it solves

A typical bot runs on an ordinary server, and the private key that signs for its account sits in a file
(often `.env`) or in memory the operator can read. Whoever can read that file can sign anything with it.
The framework's own guidance makes the same point about the agent contract: if any access key to the
agent contract's account is left, "this would allow the access key owner to withdraw the funds held by
the Shade Agent". [sa-security]

## How it works on NEAR

**Two parts.** A Shade Agent has an **agent** (off-chain: a backend service running in a TEE) and an
**agent contract** (on-chain: a NEAR smart contract). The contract "decides who can act as an agent (via
attestations, approved measurements, and PPIDs), enforces guardrails, and gives valid agents access to
on-chain signing via chain signatures (MPC signing)". One agent contract can have many registered agents,
for example several copies of the same code for redundancy. [sa-overview]

**The agent's key is made inside the TEE.** The agent's account is an **implicit account** (a 64-character
hex name) derived from the agent's **ephemeral private key**: the key and the account are unique to that
agent and change each time it reboots. The key should not be stored anywhere, including on the host.
[sa-terms] [sa-security]

**Registration.** The agent calls `register_agent` on the agent contract with its attestation and pays
0.00486 NEAR for its storage. In TEE mode the contract accepts it only if [sa-contract]:
- the attestation is a genuine TEE attestation (checked by the `shade-attestation` crate);
- its **measurements** are on the contract's approved list. There are six: MRTD, RTMR0, RTMR1, RTMR2, the
  key provider digest and the app compose hash ("constant for a given Docker Compose file and app layer
  configurations"); [sa-terms]
- its **PPID** (Provisioning Platform ID, an id of the physical TEE machine) is on the approved list;
- the attestation's report data holds the caller's own implicit account id, which "binds the attestation
  to the same TEE where the agent's key was created to prevent replay of valid attestations". The caller
  must be an implicit account ("Account ID must be implicit account").
A failed check panics with "Attestation verification failed: …". A registration stays valid for
`attestation_expiration_time_ms`. [sa-contract]

**Agent-gated methods.** `request_signature(path, payload, key_type)` first calls `require_valid_agent`.
A caller that never registered gets the panic "Agent not registered". A registered agent whose
registration expired, or whose measurements or PPID are no longer approved, is removed and the call fails
with "Invalid agent: [...]" (reasons `ExpiredAttestation`, `InvalidMeasurements`, `InvalidPpid`).
[sa-contract]

**Signing.** A valid agent's `request_signature` makes the agent contract call `sign` on the MPC contract
(`v1.signer-prod.testnet` on testnet, `v1.signer` on mainnet) with 1 yoctoNEAR attached. [sa-contract]
Because the agent contract is the caller of `sign`, the derived addresses belong to the agent contract's
account and the path (Topic 4.1: address = f(root key, predecessor account, path)). The template derives
its Ethereum address from the agent contract id and the path `"ethereum-1"`. [sa-template] [topic-4.1]
"All assets and state of the Shade Agent should be tied to the agent contract, not the agent's account,
since agent keys are ephemeral." [sa-terms]

**Changed code cannot sign.** Changed code gives different measurements (the app compose hash changes),
so it cannot register unless the owner approves those measurements. [sa-terms] [sa-contract]

**Upgrades.** The owner of the agent contract controls which measurements and PPIDs are approved and can
remove agents. A typical upgrade: approve the new measurements, give operators a transition period, then
remove the old ones. The framework recommends that the owner be a **multisig**. [sa-contract] [sa-security]

## Words to know

- **Shade Agent:** an application built with the Shade Agent Framework: an agent in a TEE plus an agent
  contract on NEAR. [sa-terms]
- **Agent:** one instance of the off-chain code running inside a TEE. [sa-terms]
- **Agent contract:** the NEAR smart contract that registers agents, enforces guardrails and gives valid
  agents chain signatures. [sa-terms]
- **Measurements:** hashes that identify the code running in the TEE and the platform it runs on. [sa-terms]
- **PPID:** an id of one physical TEE machine. [sa-terms]
- **Implicit account:** a NEAR account whose name is the hex of its public key (Topic 0.2/1.1).
- **Guardrails:** limits in the agent contract (which functions, contracts, chains or amounts) that hold
  even if a TEE is compromised. [sa-terms]

## Common misunderstandings

- **"The agent's address comes from the enclave's code hash."** No. The enclave's key is ephemeral; the
  signing addresses come from the agent contract's account and a path. [sa-terms] [sa-template]
- **"Nobody can ever change the agent."** The contract owner can approve new measurements, which is how
  upgrades work, and is also why the owner should be a multisig and the contract's access keys removed.
  [sa-contract] [sa-security]
- **"A TEE makes the key impossible to steal."** The framework's security page says TEE confidentiality "is
  not absolute": TEE.fail showed that a host with physical access can extract secrets from Intel TDX
  through side channels, which could include an agent's private keys. Hence on-chain guardrails. [sa-security]
- **"If the machine goes down, the funds are lost."** The assets sit with the agent contract, and another
  registered agent can carry on. The framework advises several identical agents on different hardware for
  liveness, and warns that the host can pause or refuse to run the agent at any time. [sa-security]

## Compared with

- **A bot with a key in `.env`:** whoever reads the file (developer, attacker, host) can sign anything.
  [sa-security]
- **A human multisig:** people approve every action; slow, but nobody depends on a TEE.
- **A Shade Agent:** code proven by attestation acts on its own, inside on-chain guardrails; the contract
  owner still controls upgrades. [sa-docs]

## Strengths and weaknesses (feeds the Honest take)

**Strengths:**
- No developer holds the agent's key: it is made inside the TEE and never stored. [sa-terms]
- Only attested, approved code can ask the agent contract for signatures; anyone else gets "Agent not
  registered". [sa-contract]
- Multichain: through chain signatures, the agent contract can sign transactions for most chains. [sa-overview]
- Assets live with the contract, so agents can restart, be replaced or run as several copies. [sa-terms]

**Weaknesses:**
- The contract owner can approve new code (new measurements). The owner is a point of trust: it should be
  a multisig, and the contract account's access keys must be removed. [sa-security]
- TEEs are not absolute: physical side-channel attacks (TEE.fail) can extract keys, so guardrails in the
  contract matter. [sa-security]
- Liveness: the host can pause the agent; you need several agents and duplicate-action protection. [sa-security]
- Status: NEAR's docs say the Shade Agent Framework is deprecated: "not maintained since April 19, 2026",
  "Do not use it for new projects". [near-docs-shade]

## What the lesson must show

1. A bot whose key sits in a `.env` file: whoever reads the file can sign.
2. An agent booting in a TEE and making its own key (an implicit account).
3. Registration: the agent contract's four checks (genuine quote, approved measurements, approved PPID,
   report data = the agent's account).
4. The developer's attempts: calling `request_signature` from their own account ("Agent not registered")
   and registering a changed copy (measurements not approved).
5. The agent's signing request: agent → agent contract `request_signature` → `sign` on the MPC contract,
   for the agent contract's derived Ethereum address.
6. Honest take, including the owner's power, TEE.fail and the deprecation.

In this book no agent or agent contract runs: the contract's checks run in the browser, written from the
reference contract, and are labelled as a model. The derived address is real math (Topic 4.1), from the
signer's root key read through the `Chain` interface (DemoChain's demo signer in demo mode).
