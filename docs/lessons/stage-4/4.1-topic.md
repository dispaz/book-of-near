# Topic 4.1: Chain Signatures and Multichain Accounts

The source of truth for lesson 4.1. The lesson script (`4.1.md`) and the code may only teach what this

## In one sentence

Using decentralized Multi-Party Computation (MPC), a single NEAR account can deterministically derive addresses and sign native transactions on any blockchain, including Bitcoin, Ethereum, Solana, and Cosmos.

## The problem it solves

Web3 is notoriously fragmented. To interact across ecosystems, a user must download multiple browser wallet extensions, write down dozens of separate seed phrases, and acquire different native gas tokens for each chain just to submit transactions. Traditional cross-chain solutions rely on vulnerable bridges or custodial intermediaries. [near-chain-sigs]

## How it works on NEAR

**Decentralized Multi-Party Computation (MPC).**
- Instead of an account holding a foreign private key directly, the root private key is split across an open, decentralized network of MPC validator nodes using threshold cryptography. [near-chain-sigs]
- The complete private key never exists on any single server or in memory at any point. [near-chain-sigs]
- Signature requests are handled by the canonical smart contract: **`v1.signer`** on mainnet and **`v1.signer-prod.testnet`** on testnet. [spike-5]

**Deterministic Address Derivation.**
- A foreign address (such as a standard Ethereum `0x...` address or Bitcoin address) is derived deterministically from three elements: [near-chain-sigs] [spike-5]
  1. The **NEAR Account ID** (e.g. `alice.near` or `bon-practice.testnet`).
  2. A **Derivation Path** string chosen by the user or application (e.g. `"ethereum-1"`, `"eth/defi"`, `"btc-vault"`).
  3. The **MPC Master Public Key**.
- Because the derivation is mathematically deterministic, derivation is calculated instantly offline (via `chainsig.js`) without needing network calls. [spike-5]
- An account can derive an infinite number of separate foreign addresses simply by varying the derivation path. [near-chain-sigs]

**The Signing Lifecycle.**
1. **Prepare:** The client application constructs the native target-chain transaction (e.g. an Ethereum transaction formatted via `viem`) and computes the 32-byte hash to be signed. [spike-5]
2. **Request Signature:** The NEAR account calls `sign({ payload, path, key_type })` on `v1.signer` attaching **1 yoctoNEAR** deposit and ~20–30 Tgas. [spike-5]
3. **MPC Consensus:** The MPC threshold nodes coordinate off-chain, compute signature shares, and produce a valid ECDSA ($r, s, v$) or EdDSA signature in ~4–6 seconds. [spike-5]
4. **Broadcast:** The client combines the signature with the target transaction and broadcasts it to the destination blockchain's RPC. [spike-5]

**The Foreign Gas Reality.**
- A newly derived Ethereum address begins with zero ETH. [spike-5]
- To execute a broadcasted transaction on Ethereum or Sepolia, the derived address must either be funded with native gas tokens, or use a paymaster/gas station relayer. [spike-5]

## Words to know

- **Chain Signatures:** NEAR's protocol feature enabling accounts and smart contracts to sign transactions for other blockchains.
- **MPC (Multi-Party Computation):** A cryptographic subfield allowing multiple parties to jointly compute a function over their inputs while keeping those inputs private.
- **Derivation Path:** A hierarchical string parameter specifying a unique sub-key or sub-account under the parent account.
- **Key Share:** A cryptographic fragment of a private key held by an individual MPC node.
- **Threshold Signature:** A signature produced when a predetermined threshold ($k$ of $n$) of MPC nodes collaborate.

## Common misunderstandings

- **"NEAR is wrapping or bridging the foreign tokens."** No. Transactions signed by Chain Signatures are 100% native on the target blockchain. An Ethereum transaction signed via NEAR executes directly on Ethereum L1. [near-chain-sigs]
- **"The NEAR validator holds my Ethereum private key."** No single validator ever possesses the private key; it only exists as distributed mathematical shares. [near-chain-sigs]
- **"Deriving a new address requires paying a transaction fee on NEAR."** No. Derivation is pure math based on the account name and path, executed offline in milliseconds for free. [spike-5]

## Compared with Bridges and Smart Wallets

- **Lock-and-Mint Bridges:** Require locking collateral in smart contracts, creating multi-billion-dollar honeypots vulnerable to hack and de-pegging. [near-bridge-risk]
- **Account Abstraction (ERC-4337):** Only works on EVM chains, requires deploying a contract wallet on every target chain, and cannot control non-smart-contract chains like Bitcoin. [near-chain-sigs]
- **NEAR Chain Signatures:** Chain-agnostic (supports ECDSA for EVM/Bitcoin and EdDSA for Solana), requires no contract deployment on the foreign chain, and uses native assets. [near-chain-sigs]

## Strengths and weaknesses (feeds the Honest take)

**Strengths:**
- True multichain control: One NEAR account controls addresses on Bitcoin, Ethereum, Solana, and beyond. [near-chain-sigs]
- Smart contract ownership: NEAR smart contracts can hold foreign addresses and programmatically sign foreign transactions (e.g. a NEAR DAO controlling an Ethereum treasury). [near-chain-sigs]
- Deterministic and free derivation: Zero cost to generate unlimited foreign addresses. [spike-5]

**Weaknesses:**
- Latency: MPC signing takes several seconds to reach threshold consensus (spike 5: about 5.5 s; live check 11 Nov 2026: 6.7 to 13.9 s from send to final, four runs), slower than local private key signing. [spike-5]
- Foreign gas bootstrap: A derived address needs foreign gas tokens (or a gas relayer) before its signed transaction can be broadcasted. [spike-5]
- Node security assumptions: Trust rests in the honesty of the threshold majority of the MPC validator set. [near-chain-sigs]

## What the lesson must show

1. Derive an Ethereum/Sepolia address from the learner's NEAR account and derivation path `"ethereum-1"`.
2. 3D visual: Show the learner's mailbox connecting to the ring of MPC validator nodes, which projects an address onto the Ethereum ledger.
3. Prepare a test Sepolia transaction and dispatch the `sign` call to `v1.signer-prod.testnet`.
4. Observe the MPC threshold countdown (~5 seconds in demo mode, ~10 seconds on testnet) as key shares assemble the signature.
5. Show how the signature appears on the Ethereum transaction: the `r` and `s` values (32 bytes each) and the recovery id `v`, attached to the transaction's signature fields.
6. Verify the recovered address matches the derived Ethereum address cryptographically using `viem` (`ecrecover` over the payload hash with `r`, `s`, `v`).

Bitcoin, Solana and Cosmos are out of scope for this lesson; they are mentioned only as protocol background, not demonstrated.
